# Архитектура и реализации

Документ описывает C++-часть репозитория и её текущую реализацию. Каталог `tui/` намеренно исключён. Проект использует C++23 и организован по модулям под `src/`.

## Каталоги и зависимости модулей

| Путь | Назначение |
| --- | --- |
| `src/common/` | Типы параметров поиска, используемые несколькими модулями. |
| `src/api/` | HTTP-запросы к `api.yani.tv`, API-модели и преобразование JSON. |
| `src/cache/` | Shared-memory heap-ы, аллокаторы, структуры и владение данными. |
| `src/core/` | Связь API с Cache, асинхронные операции, кеширование и очистка. |
| `src/server/` | Фасад над Core, локальный IPC-протокол и исполняемый сервер. |
| `src/app/` | Консольный демонстрационный/интеграционный сценарий `my_app`. |
| `cmake/` | Общие настройки компилятора, предупреждений и санитайзеров. |

Зависимость направлена от верхнего уровня к нижнему: `server -> core -> api + cache`; `app` использует Core. Cache не зависит от API. В корневом `CMakeLists.txt` включены C++23 и модули из `src/`. На Linux дополнительно подключается каталог `tui/`, который здесь не рассматривается.

## Общая последовательность работы

```text
Клиент --JSON-команда--> IpcServer -> Server -> Core -> API
   |                                          |      |
   +------ отображает heaps и читает handles <-+-- Cache
```

IPC передаёт команды, статусы и handles, а не содержимое аниме. После `hello` клиент отображает одноимённые shared-memory heaps и по паре `{segment_id, offset}` разрешает запись в своём адресном пространстве. Поэтому адрес указателя у сервера и клиента может отличаться; указатель между процессами никогда не передаётся.

## API и модели

### Модельный слой

`src/api/models.def` — единый список структур и полей API. Макросы в `models.hpp` создают C++-структуры, а `json.hpp` использует тот же список для `from_json`/`to_json`. Это уменьшает расхождения между полями модели и сериализацией. Параметры поиска объявлены отдельно в `src/common/types.hpp` как `yani::SearchInput`; каждое поле опционально, чтобы отличать не заданный фильтр.

Модели покрывают подробную запись аниме, упрощённую запись для результатов поиска, элементы feed и расписания. В подробной записи есть, среди прочего, статус, URL и варианты постера, рейтинги, тип, описание, возрастной рейтинг, внешние идентификаторы, создатели, студии, видео, жанры, порядок просмотра, переводы, ограничения, эпизоды, скриншоты и позиции в топах. Feed описывает новые аниме, объявления, рекомендации, карусель, расписание и коллекции. Точный перечень полей находится в `models.def` и намеренно не дублируется в коде преобразования Cache.

`yani_get<T>` обрабатывает пропущенное/null поле через значения по умолчанию, заданные `yani_null_value`. Для числового поля допускает JSON-число или строку, полностью разбираемую через `from_chars`; для `std::string` принимает строку или число (число сохраняется как JSON-текст); для вектора строк принимает массив строк/чисел. Остальные значения передаёт nlohmann-json. Ошибки оборачиваются именем API-поля и типом JSON. Null-маркеры отдельных типов — sentinel-значения, например `INT64_MIN` для `int64_t`, `-1` для `double`, `true` для bool; пустые строки и векторы остаются пустыми.

### HTTP-клиент

`api.hpp` предоставляет `getAnime`, `searchTitles`, `getFeed`, универсальный `get`, а также Async-варианты с `std::future<std::expected<T, ApiError>>`. Реализация находится в `api.cpp` и использует CPR. Параметры поиска превращаются в query-параметры; списки значений соединяются запятыми. Anime запрашивается по `anime/{alias_or_id}` с параметром `need_videos`. Поиск выполняется на `anime`, feed — на `feed`, опциональный `watches` также кодируется через запятую. Каждый запрос передаёт заголовок `Lang: ru`.

Общий разбор ответа отдельно проверяет сетевую ошибку CPR, JSON-синтаксис и HTTP-код 2xx. Для ошибки JSON-поля или структуры возвращается `ApiError` с HTTP-статусом и телом ответа. Async-адаптер запускает CPR callback-запрос и завершает promise результатом конвертации; исключения преобразования не выходят наружу. Синхронные методы остаются доступны, но основной Core-путь пользуется Async вариантами. Учтите, что HTTP-клиент обращается к внешнему API; без доступной сети реальные ответы не гарантированы.

## Cache и разделяемая память

### Состав heaps

`Cache` содержит статические экземпляры четырёх heap-ов. К имени кеша добавляется суффикс раскладки `.v8` и имя heap-а: `.anime`, `.variable`, `.search`, `.feed`. Например, `aniparser.v8.search`. В `hello` IPC эти имена сообщаются клиенту.

| Heap | Реализация и содержимое |
| --- | --- |
| `AnimeHeap` | Фиксированные блоки по `sizeof(Anime)`. Хранит базовые поля, дескрипторы строк/векторов, `usage_count`, `last_used_ns` и собственный handle. |
| `VariableHeap` | Блоки произвольного размера. Хранит байты строк и буферы `SharedVector<T>`. |
| `SearchHeap` | Фиксированные записи `SharedSearch`; страница содержит максимум 10 Anime handles и ссылку на следующую страницу. |
| `FeedHeap` | Фиксированные записи `SharedFeed`; сами списки, строки коллекций размещаются в `VariableHeap`, элементы являются handles аниме. |

`Anime` и записи feed/search являются trivially copyable/destructible. В них нельзя хранить `std::string`, `std::vector`, локальные указатели или другой ресурс с деструктором: такие значения не переживают remap в другом процессе. `SharedString` содержит `{segment_id, offset, size, capacity}`; `view()` разрешает handle и возвращает `string_view` в текущем процессе. `set()` переиспользует имеющийся блок, если хватает capacity, иначе выделяет новый, копирует данные и освобождает прежний. `append()` работает аналогично для добавления в конец. Пустая строка может сохранять уже выделенный блок до `clear()`.

`SharedVector<T>` по тому же принципу содержит handle буфера и размер/capacity. Тип `T` обязан быть тривиально копируемым и разрушаемым. `reserve()` увеличивает capacity геометрически (обычно x2), выделяет новый блок, копирует элементы и удаляет старый блок; `push_back()` сначала копирует входной элемент, поэтому безопасен при reallocation, если аргумент ссылался на элемент того же вектора. `clear()` оставляет память, `release()` освобождает блок. Нельзя вызывать `release()` для вложенных типов без предварительного освобождения их собственных SharedString/векторов: для Anime это централизовано в `Anime::release_shared_storage()`.

### Сегменты и аллокатор

Общий интерфейс `IHeap` определяет `create/open/close`, `allocate/deallocate`, `resolve`, `allocation_size` и число сегментов. `HeapManager` привязывает логическое имя heap-а к провайдеру, создаёт сегмент №1 или при открытии последовательно подхватывает уже существующие сегменты. Перед поиском места/разрешением более высокого ID вызывается `refresh`/открытие пропущенных сегментов, благодаря чему процесс может увидеть расширение, созданное другим процессом.

`SegmentAllocator.hpp` задаёт общий формат сегмента: заголовок с magic/version/размером и атомарными блокировками, далее последовательность заголовков блоков и payload. Все payload выровнены по 8 байт. Аллокация проходит блоки линейно, находит первый свободный подходящего размера, при необходимости делит блок. Освобождение помечает блок свободным и объединяет соседние свободные блоки. Сегмент имеет общий spin lock для метаданных; отдельный registry lock координирует критические операции с записями и их ссылками между процессами. Статистика суммирует размер сегментов, занятый/свободный payload и число блоков.

`AnimeHeap` и `SearchHeap` принимают только блоки фиксированного размера; `VariableHeap` — произвольный ненулевой размер. При нехватке места каждый heap просматривает существующие сегменты, пытается добавить новый и повторяет поиск. Начальный размер следующего сегмента удваивается; для запроса крупнее текущего выбирается как минимум размер запроса с учётом служебного overhead. При ошибке provider/инициализации возвращается пустой handle. Старые сегменты автоматически не удаляются.

### Провайдеры платформ

`IShmSegmentProvider` абстрагирует создание/открытие сегмента, освобождение локального отображения и удаление backing storage.

- `PosixShmSegmentProvider` использует `shm_open`, `ftruncate`, `mmap(MAP_SHARED)` и `shm_unlink`; применяется для POSIX-сборок Linux/macOS.
- `FileShmSegmentProvider` создаёт файлы в заданном каталоге и отображает их через `mmap(MAP_SHARED)`. Имя файла образуется из FNV-подобного 64-bit hash имени heap-а и ID сегмента. Один и тот же каталог должен быть доступен всем взаимодействующим процессам. Этот провайдер включён CMake для Android/iOS.
- `WindowsShmSegmentProvider` создаёт backing-файлы и отображения через `CreateFileW`, `CreateFileMappingW`, `MapViewOfFile`. Каталог по умолчанию у standalone сервера берётся из `%LOCALAPPDATA%\Aniparser\cache`.

Провайдеры кешируют отображения внутри процесса и считают локальные ссылки на mapping; `close_segment()` снимает mapping/дескрипторы при последнем локальном использовании. Удаление сегмента — отдельная операция и не вызывается при обычном закрытии кеша. Следовательно, данные backing storage сохраняются между перезапусками, если их явно не удалить. Важно: desktop `main.cpp` выбирает Windows, Android или Posix provider; iOS не имеет standalone server target. Встраивающий iOS-код должен создать `FileShmSegmentProvider` самостоятельно и передать общий App Group каталог, когда доступ нужен нескольким процессам приложения.

### Ссылки, время и очистка Anime

Каждый `HeapHandle` — смещение внутри конкретного сегмента, а не стабильный C++-адрес. `Cache::allocate_anime()` выделяет `Anime`, начинает его lifetime через `construct_at`, записывает `self`, устанавливает начальный usage count в 1 и трогает метку времени. `resolve_anime()` проверяет запись и обновляет last-used. `retain_anime()` атомарно увеличивает счётчик под registry lock; `release_anime()` уменьшает, не позволяя уйти ниже нуля. Sentinel `UINT64_MAX` означает, что запись уже захвачена на удаление и новые ссылки запрещены.

`find_or_create_anime(id)` под registry lock сканирует занятые блоки AnimeHeap, ищет такой `anime_id`, который не удаляется, и увеличивает его ссылку. Если не найден — выделяет и инициализирует запись. Это линейный поиск, без отдельного persistent ID-индекса. Создаваемые из API search/feed частичные аниме наполняются соответствующим подмножеством полей. Подробный ответ преобразуется функциями `store_anime`, `store_search_result` или `store_feed_item`; строки и вектора распределяются в VariableHeap, а viewing order создаёт отдельные записи Anime и ребра handles.

Ссылки на аниме удерживаются вызывающим клиентом, Search page, Feed и Anime `viewing_order`. Для освобождения payload вызывается `release_shared_storage`: освобождаются строки, вложенные векторы и child-ссылки. Счётчик аниме не равен числу всех внешних процессов напрямую — это суммарное число выданных владений/ребер, поэтому все владельцы обязаны парно вызвать release. Метка времени берётся из `steady_clock` в наносекундах; она подходит для сравнения процессов на той же машине при текущем запуске ОС, но не является календарным timestamp для передачи между перезагрузками.

## Реализация Cache-структур

### Anime

Полная схема записи описана в `src/cache/Anime.hpp`. Числовые поля хранятся непосредственно, строковые поля представлены `SharedString`, массивы — `SharedVector`. `viewing_order` — именно вектор handles на Anime-записи, а не копия структур; каждое ребро удерживает child Anime. Связи могут повторно использовать уже созданные по ID записи. `release_shared_storage()` проходит все вложенные дескрипторы и child handles, после чего их блоки VariableHeap и ссылки становятся освобождаемыми.

### Search

`SharedSearch` содержит `self`, общий `root`, `std::array<HeapHandle, 10> anime`, `anime_count`, `continuation` и `last_used_ns`. При добавлении результата SearchHeap сначала сохраняет владение ссылкой на Anime. `set_continuation()` проверяет ссылки и проходит будущую цепочку, запрещая циклы, затем назначает child общий root. `resolve_search()` обновляет время страницы и корня; обращение к любой странице поддерживает свежесть всей цепочки.

Удаление любого page handle находит root, атомарно помечает его удаляемым и освобождает всю цепочку: у каждой страницы снимаются ссылки на аниме, затем освобождаются записи страниц. Очистка выбирает только корневые страницы, проверяет всю цепочку и её самое новое время использования; удаляет цепочку целиком только если все страницы старше cutoff. При конкуренции с retain/resolve registry lock и sentinel не позволяют очистке уничтожить используемый объект.

### Feed

`SharedFeed` содержит значения сезона/года карусели и векторы handles: `new_anime`, `announcements`, `recommendations`, `carousel_items`, `schedule_items`; также вектор `SharedFeedCollection`. Коллекция хранит id, SharedString заголовка/описания и SharedVector Anime handles. Расписание также представлено ссылками на Anime-записи, частично заполненные полями schedule. При `deallocate(feed)` все векторы ссылок освобождаются с уменьшением Anime reference count; затем освобождаются строки коллекций и блоки векторов. FeedHeap сам по себе не реализует refcount или TTL для feed handle — освобождение выполняет получивший его клиент.

## Core: преобразование, кеши и фоновые задачи

### Инициализация и жизнь

Core держит ссылку на provider, имя кеша и размеры начальных Anime/Variable сегментов (по умолчанию 8 и 32 MiB). `initialize()` сначала пробует `Cache::open`, затем `Cache::create`; при успехе запускает `std::jthread` обслуживания. Деструктор запрещает новые задачи обновления, останавливает maintenance thread, дожидается сохранённых `std::future<void>` задач, затем закрывает Cache. Статическая природа Cache означает, что одновременные независимые экземпляры Core с разными mapping в одном процессе не поддерживаются.

### Получение аниме

Синхронная перегрузка `getAnime(string_view, need_videos)` напрямую вызывает API, выделяет новую Anime-запись и сохраняет полный результат. Она возвращает `Result<HeapHandle>`, поэтому ошибка API или размещения передаётся как `unexpected(ApiError)`.

Асинхронная перегрузка `getAnime(int64_t, callback)` предназначена для быстрого ответа клиенту. Под mutex она ищет локальную `AnimeEntry` по ID; первый запрос создаёт shared slot и ставит обновление, следующий запрос получает retained reference на существующий slot. `AnimeEntry` хранит handle, состояние `updating`, признак `loaded_full`, время последнего API вызова и ожидающие callbacks. Если обновление уже выполняется, callback добавляется к нему; новая API-задача на тот же ID не создаётся. Иначе, если с прошлого API-запроса прошло больше пяти минут, запускается `std::async(std::launch::async, ...)`.

Worker фиксирует время непосредственно перед API-запросом, получает полную модель через `getAnimeAsync`, строит временный `Anime replacement`, затем освобождает старые переменные данные и копирует payload в тот же слот. При этом сохраняются usage count, last-used и идентичность handle. Callbacks вызываются после снятия mutex, каждый в try/catch, чтобы ошибка одного callback не остановила остальных. При ошибке API/конвертации/записи callback получает `nullptr`. Возвращённый из Core слот принадлежит вызывающему коду; в сценарии Server владение передаётся как handle.

Есть тонкость текущей реализации: флаг `loaded_full` устанавливается при успешном обновлении и используется в ответном статусе сервера. Процессная карта `anime_by_id_` и timestamps пропадают при рестарте; shared-memory Anime record при этом может остаться. Если карта Core пуста, сервер считает запись требующей обновления и создаёт/получает слот по ID.

### Search

`Core::searchTitles(params, callback)` возвращается после постановки фоновой задачи. Задача начинает с `max(0, params.offset)` и для каждой страницы фиксирует `limit=10`, формирует ключ JSON-массивом всех фильтров в стабильном порядке, включая offset/limit. Значение `search_cache_` — исходный `vector<SearchResult>` и время запроса, хранится только в RAM процесса.

Для свежего кеш-ключа API не вызывается; из сохранённых моделей формируется новая shared page. Для устаревшего ключа старая страница сначала материализуется в SearchHeap и передаётся callback, затем запускается API обновление. Timestamp обновляется в момент обращения к API, а не просто при чтении кеша. При успешном API-ответе актуализируется process cache, строится новая shared page и вызывается callback второй раз. На cache miss запрос API выполняется до первого callback. Ошибка возвращает callback с `nullptr`.

Каждая shared page включает до десяти результатов. Anime-слоты находятся через `find_or_create_anime`; только что созданные слоты получают поля из SearchResult, уже существующие записи повторно не перезаписываются частичной моделью. SearchHeap удерживает Anime ссылкой. Callback возвращает bool: `true` — Core увеличивает offset на 10 и запрашивает следующую страницу; `false` завершает цепочку. Пагинация прекращается также при ответе меньше 10 элементов или переполнении offset. `searchPageNeedsRefresh()` нормализует offset/limit тем же способом и сообщает устаревание только для уже закешированного ключа.

IPC специально использует callback, который возвращает `false`: один `getSearch` выдаёт одну страницу, а клиент самостоятельно отправляет следующий запрос с offset+10. Обратите внимание: при stale refresh callback может вызываться для старой и новой страницы; клиенты должны освободить handle старого результата после переключения на новый.

### Feed

`getFeed(watches, callback)` также работает в фоновой задаче. Ключ кеша — JSON-представление вектора watches, а значение — модель `FeedResponse` в памяти Core. Свежий результат преобразуется в новый SharedFeed без API-запроса. Устаревший сначала преобразуется и передаётся callback, после чего Core запрашивает API; новый FeedResponse кешируется и превращается в другой SharedFeed. При отсутствии кеша сначала выполняется API. Ошибка запроса или размещения передаёт `nullptr`.

При создании Feed для каждой группы элементов выделяются/переиспользуются Anime slots. Поля отображаются из разных feed-моделей подходящими функциями преобразования; каждый список добавляет Anime handle через `FeedHeap::append_anime`, который удерживает ссылку. `getFeed()` не переиспользует один и тот же SharedFeed handle на повторных запросах: он строит новый снимок, а клиент обязан освободить предыдущий. Process cache Search/Feed и timestamps чистятся от старых ключей при успешном новом API-запросе, но это не персистентное хранилище.

### Фоновая очистка

Поток обслуживания ждёт пять минут между проходами. Затем cutoff вычисляется как `steady_clock::now() - 20 min`. SearchHeap удаляет устаревшие Search root chains; Cache выбирает по одной самой старой нулевой Anime-ссылке за итерацию и удаляет до cutoff. Активные ссылки препятствуют удалению независимо от возраста. Само получение Anime через `resolve_anime`, retain/release, обращение к Search обновляет метки последнего использования. Feed не входит в отдельный TTL cleanup: он живёт до `deleteFeed`/освобождения владельцем, при котором освобождаются связанные ссылки.

## Server и протокол IPC

### Фасад

`Server` не хранит данные отдельно: это адаптер типов. Он вызывает Core, превращает `Anime*` в `Anime::self`, `SharedSearch*` в корневой Search handle и `SharedFeed*` в Feed handle. Методы `deleteAnime`, `deleteSearch`, `deleteFeed` делегируют release соответствующего владения Cache/Core.

### Транспорт и конкурентность

На POSIX `IpcServer` использует поток accept и отдельный worker-поток для клиента. Сообщения читаются из byte stream до `\n`, допускается несколько команд в одном чтении; одна команда больше 1 MiB отклоняется. Ответы сериализуются как JSON + newline, запись в соединение защищена mutex. При запуске удаляется только устаревший socket-файл: если путь не является socket или к нему можно подключиться, запуск отказывается его заменять. Socket создаётся с правами `0600`. `stop()` прекращает accept, прерывает клиентские сокеты и дожидается потоков.

В Windows используется Named Pipe byte stream с отклонением удалённых подключений, отдельным потоком для подключённых клиентов и теми же newline JSON-сообщениями. Реализация Windows дублирует формат команд/ответов, но использует системные операции `CreateNamedPipeW`, `ConnectNamedPipe`, `ReadFile`/`WriteFile`.

Все запросы — JSON object с `id` и `method`. Ответ успеха имеет `{"id": ..., "ok": true}`; ошибка — `ok:false` и `error`. Значения `id` повторяются в поздних event-сообщениях.

| Метод | Вход | Результат |
| --- | --- | --- |
| `hello` | Только `id`, `method` | `protocol:1`, `layout:8`, имена и snapshot числа сегментов всех heaps; у файловых провайдеров также `shared_memory_directory`. |
| `getAnime` | `anime_id` | Немедленный Anime handle, `loaded`, `refreshing`; позже `anime.updated` с тем же id запроса, Anime handle и `ok`. |
| `getSearch` | `params` — поля `SearchInput` | Одна страница, handle корня цепочки, `offset`, `limit:10`; stale обновление дополнительно приходит как `search.updated`. |
| `getFeed` | Необязательный `watches` | Feed handle; stale обновление — `feed.updated`. |
| `deleteAnime` | Anime handle | `deleted` — удалось ли снять Anime reference. |
| `deleteSearch` | Search handle страницы/корня | `deleted` — удалось ли уничтожить цепочку Search. |
| `deleteFeed` | Feed handle | `deleted` — удалось ли освободить Feed и его Anime-ссылки. |

Handle кодируется как `{"segment_id":N,"offset":N}` или `null`. `hello.heaps.*.segments` — snapshot, а не обещание, что дополнительных сегментов не появится. Клиенту нужно отображать новые сегменты, если полученный handle указывает на неизвестный ID. `layout` обязателен для проверки совместимости памяти; после изменения ABI shared structs версию необходимо поднять и согласовать с клиентами. Названия методов и поля параметров являются частью протокола.

### Выбор платформы и запуск сервера

`src/server/main.cpp` принимает аргументы `[cache-name] [endpoint] [data-directory]`. Cache по умолчанию — `aniparser`. Endpoint — `/tmp/aniparser.sock` на обычных POSIX системах, `\\.\pipe\aniparser` на Windows; Android требует endpoint и каталог от вызывающего приложения. Windows по умолчанию использует каталог под LocalAppData. Desktop standalone target `aniparser_server` не собирается для Android/iOS. На Android standalone main выбирает File provider и требует каталог аргументом; для iOS сервис должен встраиваться в приложение и настраивать File provider/socket с путями контейнера/App Group самостоятельно.

Сервер сначала инициализирует Core/Cache, потом начинает слушать endpoint. Ошибка инициализации кеша или bind/listen завершает старт с ненулевым кодом. SIGINT/SIGTERM останавливают IPC и затем Core. Shared-memory backing storage не удаляется при штатном `Cache::close()`.

Подробные краткие примеры протокола также есть в `src/server/IPC.md`.

## Сборка и исполняемые цели

В Linux `flake.nix` объявляет dev shell с CMake, Ninja, GCC, Boost, nlohmann-json, CPR, curl, ncurses/notcurses, OpenSSL и pkg-config. Базовые команды:

```sh
nix develop
cmake -S . -B out/Debug -DCMAKE_BUILD_TYPE=Debug
cmake --build out/Debug -j2
```

Требуется CMake 3.25+ и C++23. Основные библиотеки: `common` (заголовочные типы), `api`, `cache`, `core`, `server`. На UNIX desktop добавляется `my_app`, кроме Android/iOS; `aniparser_server` добавляется, если не Android/iOS. Сборка cache на Linux проверяет, доступен ли `shm_open` из libc, и только при необходимости линкует `rt`. Форматирование C++ задаётся `.clang-format`: два пробела, ширина 80 колонок. Универсального тестового target и `ctest` набора нет; `my_app` запускает сценарий проверки API/cache, а `src/api/test.cpp` отдельно не включён как тестовая цель.

Пример запуска backend:

```sh
out/Debug/src/server/aniparser_server aniparser /tmp/aniparser.sock
```

`src/app/main.cpp` демонстрирует прямой Core API: тестирует полную загрузку ID 771 и 4958, печатает имя/статистику heap, асинхронность callback, ищет «наруто», получает первые три Anime и сценарий feed. Это ручная интеграционная программа и требует доступа к API.

## Практические правила изменения кода

1. Новые `.cpp` включайте в `CMakeLists.txt` соответствующего модуля, public headers добавляйте в FILE_SET.
2. Общие API-модели описывайте в `models.def`; search-параметры поддерживайте согласованными в JSON IPC-парсерах POSIX и Windows.
3. При изменении Anime/SharedSearch/SharedFeed или allocator header учитывайте межпроцессную ABI-совместимость, layout version `v8`, ответ `hello` и реализацию чтения клиента.
4. Для нового shared-memory поля выбирайте trivially-copyable дескриптор/handle; строки и динамические массивы размещайте через VariableHeap.
5. Каждому `retain` должен соответствовать ровно один `release`. На ошибочных путях освобождайте уже выделенные вложенные строки/векторы и references.
6. Не держите registry lock во время callback или сетевого запроса. Callbacks могут выполнять пользовательский код и обращаться к другим heaps.
7. Следуйте `.clang-format`; форматируйте только изменённые C++-файлы. Build output и локальные generated файлы держите в `out/`.
