# Архитектура и работа приложения

В документе описаны C++-бэкенд и исполняемое приложение для разработки. Клиент из каталога `tui/` не рассматривается. Проект использует C++23 и разделён на модули `api`, `cache`, `core`, `server` и `app` в каталоге `src/`.

## Поток данных

```text
локальный клиент -> Server / IPC -> Core -> API (api.yani.tv)
                                      |       |
                                      +-> Cache <-+
```

Модуль `api` отправляет HTTP-запросы и преобразует JSON в типизированные модели `yani`. `core` координирует асинхронные запросы, сохраняет модели в разделяемую память и управляет обновлением и очисткой данных. `server` предоставляет фасад над Core и локальный IPC-транспорт. Клиент получает handles, подключает heaps разделяемой памяти и читает записи напрямую.

## Модуль API

Файл `src/api/models.def` задаёт схему моделей, объявленных в `models.hpp`; `json.hpp` генерирует функции преобразования JSON на её основе. Преобразование допускает отсутствующие и null-поля, числовые строки для арифметических полей и числа в текстовых полях. При неверных типах возвращается `ApiError` с контекстом ответа. В `api.cpp` формируются параметры запросов для получения аниме, поиска и ленты, устанавливается заголовок `Lang: ru`, обрабатываются ошибки HTTP и транспорта. `api.hpp` предоставляет синхронные и асинхронные функции; Core обычно использует асинхронные варианты. `src/api/test.cpp` — отдельный исходный файл, а не настроенная цель тестирования.

## Кеш в разделяемой памяти

`Cache` из `src/cache/` управляет четырьмя heaps. Имена строятся из заданного имени кеша и суффикса версии, например `aniparser.v8.anime` и `aniparser.v8.variable`.

- **AnimeHeap** хранит записи `Anime` фиксированного размера. В них находятся скалярные значения и handles или дескрипторы переменных данных; локальных владеющих указателей в записи нет.
- **VariableHeap** хранит строки и буферы элементов `SharedVector<T>`. `SharedString` и `SharedVector` содержат компактные дескрипторы с сегментом, смещением и размером, поэтому данные можно разрешить в любом процессе, подключившем те же heaps.
- **SearchHeap** хранит страницы `SharedSearch` фиксированного размера — до 10 handles аниме на страницу. Страницы соединены handle продолжения и имеют общий handle корня; удаление или очистка корня освобождает цепочку и ссылки на аниме.
- **FeedHeap** хранит записи `SharedFeed` фиксированного размера. Списки и метаданные коллекций находятся в VariableHeap и содержат handles аниме, а не копии элементов ленты.

Все постоянные ссылки представлены `HeapHandle {segment_id, offset}`. Полученный из handle указатель действителен только в отображении текущего процесса, используйте его кратковременно и не передавайте через IPC. Счётчик ссылок аниме учитывает handles клиентов и связи из поиска, ленты и `viewing_order` другого аниме. `retain_anime` и `release_anime` меняют владение и время последнего использования. Очистка захватывает только записи с нулевым числом ссылок, освобождает их переменные данные и удаляет запись. Поэтому клиент должен освобождать каждый полученный handle после использования. Если Core вернул сырой указатель, вызывающая сторона должна освободить соответствующую ссылку.

`HeapManager` управляет нумерованными сегментами heap и обновляет отображения, если другой процесс добавил сегмент. Аллокатор хранит метаданные блоков в сегментах, сериализует изменения общими атомарными блокировками, повторно использует и объединяет свободные блоки. Если места не хватает, он пытается добавить сегмент. Ошибки создания или отображения сегмента и нехватка памяти возвращаются как неверный handle или `false`; вызывающий код должен это обработать. `IShmSegmentProvider` скрывает платформенный способ отображения: POSIX shared memory на Linux/macOS, отображаемые файлы на Windows, общие отображаемые файлы на Android/iOS. Файловым провайдерам нужен один и тот же общий каталог во всех процессах. Heap-объекты `Cache` статические, поэтому один процесс должен использовать только одно активное отображение кеша за раз.

## Core: запросы, обновление и очистка

`Core::initialize()` подключает существующие heaps либо создаёт их, затем запускает поток обслуживания. `getAnime(id, callback)` получает или создаёт слот аниме, удерживает ссылку и сразу возвращает указатель. Фоновая задача загружает полные данные и заменяет содержимое записи в shared memory, сохраняя её идентификатор и метаданные владения. Параллельные запросы одного ID присоединяют callbacks к текущему обновлению. При успехе callbacks получают тот же слот аниме, при ошибке — `nullptr`. Полная запись не запрашивается повторно в течение пяти минут после последнего обращения к API. Поиск и лента могут создать неполный слот аниме; последующий запрос деталей заполняет его.

Перегрузка `getAnime(alias_or_id, need_videos)` работает синхронно: загружает полные данные, выделяет запись, сохраняет её и возвращает handle либо ошибку API/кеша. Полученный handle принадлежит вызывающей стороне и должен быть освобождён.

Поиск всегда нормализует размер страницы до `limit=10`, а `offset` — до неотрицательного значения. Core может переходить к следующим страницам с шагом 10, если callback просит продолжить. Результаты поиска создают или используют существующие слоты аниме и связывают их со страницами `SharedSearch`. Ответ ленты преобразуется в `SharedFeed` и ссылки на аниме. Ответы поиска и ленты кешируются в памяти процесса по полному набору параметров; ключ ленты — список `watches`. Срок кеша — пять минут. Пока кеш свежий, API не вызывается. Для устаревшего поиска или ленты Core сначала передаёт старый результат в shared memory, затем обновляет его в фоне и при успехе вызывает callback повторно. При отсутствии кеша сначала выполняется запрос API. Кеши ответов API и время обновления аниме существуют только в памяти процесса и сбрасываются при перезапуске бэкенда, хотя сами записи shared memory могут сохраниться.

Каждые пять минут Core удаляет неиспользуемые более двадцати минут записи аниме и цепочки Search. Для удаления аниме необходим нулевой счётчик ссылок: действующая ссылка из ленты, поиска или `viewing_order` сохраняет запись. Feed освобождает владелец через свой handle; фоновая очистка по времени на него не распространяется. Таким образом, удаление определяется ссылками и временем последнего использования, а не только возрастом данных API.

## Server и IPC-клиенты

`Server` преобразует callbacks и указатели Core в handles. `IpcServer` принимает локальные подключения и обрабатывает JSON-запросы, разделённые переводом строки. У каждого запроса есть `id` и `method`; ответы и асинхронные события содержат тот же ID. В Linux/macOS используется Unix domain socket (стандартный путь для настольного запуска — `/tmp/aniparser.sock`), в Windows — именованный канал. В сборках Android/iOS исполняемый сервер для настольной ОС не создаётся: встраивающее приложение передаёт свой путь к сокету и общий каталог данных.

Сначала отправьте `{"id":1,"method":"hello"}`. Ответ содержит версии протокола и раскладки, имена четырёх heaps и текущие числа сегментов. Клиент отображает эти heaps соответствующим платформенным провайдером, локально разрешает handles и при необходимости подключает новые сегменты. `getAnime` сразу возвращает handle и флаги `loaded`/`refreshing`; завершение загрузки приходит событием `anime.updated`. `getSearch` принимает `params` и возвращает одну страницу; для следующей страницы увеличьте `offset` на 10. Устаревшие данные могут сопровождаться событием `search.updated`. `getFeed` принимает необязательный массив `watches` и может позже отправить `feed.updated`. Освобождайте полученное владение командами `deleteAnime`, `deleteSearch` или `deleteFeed`, передавая соответствующий handle. Параметры поиска и примеры сообщений описаны в [`src/server/IPC.md`](src/server/IPC.md).

Транспорт предназначен для локального IPC, а не сетевого доступа. Клиенту следует проверить версии из `hello` до чтения shared-memory структур, связывать события с запросами по ID, подключать новые сегменты и освобождать старые handles после замены обновлёнными.

## Сборка и запуск

Для Linux окружение разработки описано в Nix flake. Настроить и собрать проект можно командами:

```sh
nix develop
cmake -S . -B out/Debug -DCMAKE_BUILD_TYPE=Debug
cmake --build out/Debug -j2
```

Нужны CMake 3.25+, компилятор C++23, Boost, nlohmann-json, cpr и OpenSSL. Цели включают статические библиотеки `api`, `cache`, `core` и `server`; в настольной сборке также создаются `aniparser_server` и `my_app`. Запуск бэкенда: `out/Debug/src/server/aniparser_server [cache-name] [endpoint] [data-directory]`. Значения по умолчанию и требования платформенных провайдеров заданы в `src/server/main.cpp`. `my_app` — демонстрационное приложение для проверки аниме, поиска по «Наруто» и ленты. Интегрированной системы тестирования и набора `ctest` нет. Для других платформ проверяйте список доступных целей сборки.

## Рекомендации по изменениям

Храните код модуля рядом с его настройками CMake. Публичные структуры shared memory должны оставаться тривиально копируемыми и разрушаемыми; не добавляйте в них локальные указатели, `std::string` или владеющие контейнеры. При изменении раскладки обновите версию и имена heaps, а при необходимости — версию IPC: клиентам нельзя читать несовместимые структуры. Соблюдайте `.clang-format` (два пробела, ширина строки 80 символов); форматируйте изменённые C++-файлы командой `clang-format -i`. Сгенерированные файлы сборки храните в игнорируемом каталоге `out/`.
