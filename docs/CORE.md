# Core: кэш, обновления и фоновые запросы

`Core` находится в `src/core/core.hpp` и `src/core/core.cpp`. Он владеет API
снимками в памяти процесса. `Server` вызывает Core, но не копирует его кэш и
не принимает решений о TTL.

## Что хранится

- Anime: map по `anime_id`, значение `AnimeResult`, время обновления, признак
  полноты, флаг текущего запроса и callbacks ожидающих клиентов.
- Search: map по ключу всех параметров поиска, результаты и время обновления.
- Feed: последнее значение feed, время обновления, флаг запроса и callbacks.

Полные модели — owning C++ values. Для защиты map и состояния используется
`Core::mutex_`. Не вызывайте callback под этим mutex: callback IPC пишет в
сокет и не должен блокировать доступ к кэшу. Текущий код сначала копирует
callbacks/данные, снимает lock, затем уведомляет клиентов.

## Как проходит обновление

1. Запрос читает snapshot под lock и проверяет возраст записи.
2. Callback немедленно получает текущий snapshot. Это может быть пустое значение
   или частичная запись, полученная из Feed/Search.
3. Если TTL истёк, Core помечает запись `updating` и отправляет работу в
   `TaskPool`.
4. Worker выполняет синхронную функцию `yani::getAnime`, `searchTitles` или
   `getFeed`. Синхронный вызов здесь безопасен: worker pool выделен именно для
   этой работы.
5. Результат записывается в кэш под lock; callbacks копируются из записи.
6. Вне lock успешный результат передаётся callback как обновлённый.

Один Anime не загружается параллельно несколько раз: пока `updating == true`,
новый клиент добавляет callback к существующей задаче. Feed также объединяет
ожидающие callbacks. Search использует отдельный флаг `search_updating_` на
каждый точный ключ фильтров.

## Пул задач

`TaskPool tasks_{4, 128}` создаёт 4 worker-потока и разрешает до 128 ожидающих
задач в очереди. Когда очередь заполнена, `submit()` ждёт свободное место;
когда пул остановлен, он отклоняет новую задачу. Worker ловит исключения задачи,
чтобы не умереть и не оставить очередь без обработчика.

При завершении `Core` вызывает `shutdown()`. Пул перестаёт принимать задачи,
будит ожидающие submit и workers, а workers завершают уже поставленные задачи.
Не сохраняйте ссылки на Core за пределами его жизненного цикла: фоновые lambdas
захватывают `this`.

## Успехи и ошибки

- Успех Anime заменяет запись полным API-ответом и ставит `has_full_details`.
- Ошибка Anime сохраняет старый snapshot, очищает `updating` и передаёт
  callback `ApiError`.
- Успех Search сохраняет страницу и добавляет краткие данные найденных аниме
  в Anime-кэш.
- Успешный Feed сохраняется и также добавляет краткие Anime-записи из feed.
- Ошибка Search/Feed сохраняет старые данные и пишет причину в stderr. В текущем
  IPC-протоколе клиент не получает отдельное событие ошибки Search/Feed.

`safe_api_call` превращает C++ исключение в `ApiError`, чтобы оно не покинуло
worker. Сетевые/API ошибки также пишутся в stderr с именем операции, статусом и
сообщением. Anime logging дополнительно печатает готовую команду `curl`.

## Изменение поведения Core

Если меняете кэш или callbacks:

1. Опишите, когда значение считается свежим и что именно получает первый
   callback.
2. Проверьте coalescing: параллельные запросы к одной записи должны делить
   работу и получить собственные callbacks.
3. Не вызывайте callback и не делайте HTTP под `mutex_`.
4. На ошибке очищайте флаг обновления и callback-очередь, не удаляя последний
   успешный snapshot.
5. Сверьте события/ошибки с [IPC-документом](../src/server/IPC.md) и обновите
   [описание кэша](CACHE.md).

Подробности лимитов и частичных записей см. в [CACHE.md](CACHE.md).
