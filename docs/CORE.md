# Core: кэш, обновления и фоновые запросы

`Core` объявлен в `src/core/core.hpp`. Реализация разделена по назначению:
`core.cpp` — жизненный цикл, `task_pool.cpp` — очередь API-задач,
`anime_service.cpp` — Anime-подписки, `search_feed.cpp` — Search и Feed,
`history.cpp` — история, избранное и статусы. Core владеет API-снимками в памяти
процесса. `Server` вызывает Core, но не копирует кэш и не решает, когда
обновлять данные.

## Что хранится

- Anime: отдельный `AnimeCache`. Он владеет объектами `AnimeEntry` через
  `unique_ptr`, а Core сериализует обращения к его методам своим mutex.
  Запись хранит `AnimeResult`, времена обновления и полноту, активные
  подписки с токенами и ключи Search-страниц, которые на неё ссылаются.
- Search: map по ключу всех параметров поиска, только упорядоченные ссылки
  `anime_id` и время обновления. Search snapshots собираются из общего Anime-кэша.
- Feed: последнее значение feed, время обновления, флаг запроса и callbacks.
- History: двусвязный список ID от последнего просмотра к более ранним и hash
  map `anime_id → iterator` для O(1) перемещения и удаления. Список ограничен
  1000 ID. `subscribeHistory(offset, limit)` отдаёт snapshot одной страницы;
  подписка получает новые полные snapshots только при изменении её страницы.
  `sequence` упорядочивает события внутри одной подписки, а `revision` отмечает
  изменения истории и состояния просмотра.
- Favorites: отдельный список на том же базовом классе `AnimeCollection`, с hash
  индексом и лимитом 1000 ID. Повторное добавление перемещает ID в начало.
  Подписки `subscribeFavorites` и `favorites.updated` независимы от истории;
  карточки загружаются тем же Search-запросом по ID.
- Anime states: `planned`, `watched`, `completed`, `dropped` — четыре отдельные
  коллекции `AnimeStatusCollection`, производные от `AnimeCollection`. При
  добавлении Core удаляет ID из остальных статусов под mutex и увеличивает
  revisions всех затронутых списков. `getStatus` возвращает 0 (нет статуса),
  1 (planned), 2 (watched), 3 (completed), 5 (dropped).
- Карточки истории, избранного и статусов берутся из общего краткоживущего
  Anime-кэша. Для ID текущей страницы без карточки или с карточкой старше пяти
  минут Core делает Search API-запрос по ID; весь список не загружается разом.
  Отсутствующий в API ID тоже отмечается проверенным на пять минут; отрицательный
  кэш ограничен 1000 ID и вытесняет самый старый результат при заполнении.
- AnimeSaveData хранится отдельно по `anime_id` и содержит player, dubber,
  episode и время просмотра. IPC `getAnimeSaveData` читает его независимо от
  наличия ID в списке, `updateAnimeSaveData` обновляет и сохраняет его.
  Подписки списков независимы и снимаются отдельным `unsubscribe...` методом
  или при закрытии соединения. Для Anime подписка снимается также при
  `unsubscribeAnime` и закрытии клиента.

Полные модели — owning C++ values. Для защиты map и состояния используется
`Core::mutex_`. Callback вызывается вне этого mutex, чтобы запись IPC в сокет
не блокировала доступ к кэшу. Изменения коллекций и запись файла сериализуются `collection_save_mutex_`.
Owning snapshots уведомлений ставятся в FIFO; callbacks выполняются после
освобождения locks. Повторная мутация из callback безопасна; события сохраняют
порядок sequence. Первый snapshot подписки всегда предшествует её обновлениям.

## История и SaveManager

`SaveManager` загружает историю, избранное и состояние просмотра в конструкторе
Core и сохраняет их после изменения любой коллекции или `updateAnimeSaveData`.
Файл `history.json` содержит `history`, `favorites`, списки в `anime_states`
и состояние просмотра в `save_data`. Формат версии 4; SaveManager читает версии
1–3 и переносит историю, прогресс и избранное.
Запись сначала пишется во временный файл в том же каталоге, затем атомарно
заменяет основной файл. Повторный `anime_id` удаляется из списка и добавляется
в начало; индекс в hash map позволяет найти его за ожидаемое O(1). Для статусов
добавление также убирает ID из трёх других списков. Файл
сохраняется под отдельным mutex после снятия `Core::mutex_`, чтобы операции API
не ждали запись на диск.

Каталоги хранения: Linux — `$XDG_DATA_HOME/aniparser` или
`$HOME/.local/share/aniparser`; macOS — `$HOME/Library/Application Support/AniParser`;
Windows — `%APPDATA%/AniParser` с резервным `%LOCALAPPDATA%/AniParser`. Android
может задать приватный каталог приложения через `ANIPARSER_DATA_DIR`; если он
не задан, используется `$HOME/.local/share/aniparser`, если `HOME` доступен.
Переменная `ANIPARSER_DATA_DIR` переопределяет каталог на всех платформах.
Данные каталога предназначены для одного экземпляра сервера.

## Как проходит обновление

1. Запрос читает snapshot под lock и проверяет возраст записи.
2. Callback немедленно получает текущий snapshot. Это может быть пустое значение
   или частичная запись, полученная из Feed/Search.
3. Если TTL истёк, Core помечает запись `updating` и отправляет работу в
   `TaskPool`.
4. Worker выполняет синхронную функцию `yani::getAnime`, `searchTitles` или
   `getFeed`. Синхронный вызов здесь безопасен: worker pool выделен именно для
   этой работы.
5. Результат записывается в кэш под lock; callbacks копируются из записи.
6. Вне lock успешный результат передаётся callback как обновлённый.

Один Anime не загружается параллельно несколько раз: пока `updating == true`,
новый клиент добавляет callback к существующей задаче. Feed также объединяет
ожидающие callbacks. Search использует отдельный флаг `search_updating_` на
каждый точный ключ фильтров.

## Пул задач

`TaskPool tasks_{4, 128}` создаёт 4 worker-потока и разрешает до 128 ожидающих
задач в очереди. Когда очередь заполнена или пул остановлен, `submit()`
немедленно отклоняет задачу. Caller сбрасывает флаг обновления и сообщает ошибку;
worker не ждёт места в собственной очереди. Worker ловит исключения задачи,
чтобы не умереть и не оставить очередь без обработчика.

При завершении `Core` вызывает `shutdown()`. Пул перестаёт принимать задачи,
будит workers и отбрасывает ещё не начатые задачи. Активные HTTP-запросы
завершаются в пределах своих timeout, затем workers join-ятся. Обычный
`TaskPool::shutdown()` без discard_pending по-прежнему дренирует очередь.
Не сохраняйте ссылки на Core за пределами его жизненного цикла: фоновые lambdas
захватывают `this`.

## Успехи и ошибки

- Успех Anime заменяет запись полным API-ответом и ставит `has_full_details`.
- Ошибка Anime сохраняет старый snapshot, очищает `updating` и передаёт
  callback `ApiError`.
- Успех Search сохраняет ID страницы и добавляет краткие данные найденных
  аниме в общий Anime-кэш. Строки ответа callback формируются из Anime-кэша.
- Успешный Feed сохраняется и также добавляет краткие Anime-записи из feed.
- Ошибка Search/Feed сохраняет старые данные, пишет причину в stderr и вызывает
  optional ErrorCallback. IPC завершает ожидание `search.updated`/`feed.updated`
  с `ok:false`, `error`, `status`, `refreshing:false`. Ошибка metadata refresh
  приходит в snapshot коллекции с `reason:"error"`, `refreshing:false`;
  немедленного бесконечного retry нет.

`safe_api_call` превращает C++ исключение в `ApiError`, чтобы оно не покинуло
worker. Сетевые/API ошибки также пишутся в stderr с именем операции, статусом и
сообщением. Anime logging дополнительно печатает готовую команду `curl`.

## Изменение поведения Core

Если меняете кэш или callbacks:

1. Опишите, когда значение считается свежим и что именно получает первый
   callback.
2. Проверьте coalescing: параллельные запросы к одной записи должны делить
   работу и получить собственные callbacks.
3. Не вызывайте callback и не делайте HTTP под `mutex_`.
4. На ошибке очищайте флаг обновления и callback-очередь, не удаляя последний
   успешный snapshot.
5. Сверьте события/ошибки с [IPC-документом](../src/server/IPC.md) и обновите
   [описание кэша](CACHE.md).

Подробности лимитов и частичных записей см. в [CACHE.md](CACHE.md).

## Транзакции, лимиты и автономные проверки

Методы add/remove/update возвращают `yani::Result<bool>`: unexpected — ошибка
хранения/валидации, false — операция не применилась (например, отсутствующий ID),
true — применена. Проверять нужно и Result, и его boolean значение.
Сначала строится кандидат, затем атомарно записывается файл, после этого под
mutex публикуются память и revisions. При ошибке до rename память не меняется.
Если rename прошёл, а синхронизация каталога не удалась, память соответствует
файлу, но возвращается ошибка с `data.committed:true`: durability не подтверждена.

Повреждённый, неподдерживаемый или недоступный исходный файл защищён от
перезаписи. После восстановления файла нужен перезапуск Core. Версии 1–4
поддерживаются; missing-файл означает новое пустое хранилище.

Прогресс ограничен 10 000 новыми ID; уже загруженный прогресс не удаляется
автоматически. Существующие записи можно обновить при полном лимите;
`removeAnimeSaveData(id)` освобождает место. Player/dubber ограничены 4096
байтами, episode — 256; удаление истории по-прежнему не удаляет прогресс.
Core загружает полные Anime вместе с videos, включая вызов с прежним
`need_videos=false`, чтобы coalescing не выдавал неполные данные другим callers.
Прямой `yani::getAnime(..., false)` сохраняет прежний смысл.

`Core::ApiBackend` позволяет подставить offline backend для проверок;
обычный конструктор по-прежнему использует реальные API. CallbackQueue
упорядочивает initial/update даже при быстром параллельном refresh.
Optional output `bool *refreshing` устанавливается синхронно под lock при
чтении initial snapshot; IPC не вычисляет его повторно по изменившемуся кэшу.

Revision увеличивается только при реальном изменении содержимого/порядка
коллекции или прогресса входящего в историю ID. Повторный add уже первого ID
или update теми же данными успешно завершается без фиктивного увеличения revision.
