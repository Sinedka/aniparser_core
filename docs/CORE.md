# Core и жизненный цикл данных

## Core: преобразование, кеши и фоновые задачи

### Инициализация и жизнь

Core держит ссылку на provider, имя кеша и размеры начальных Anime/Variable сегментов (по умолчанию 8 и 32 MiB). `initialize()` сначала пробует `Cache::open`, затем `Cache::create`; при успехе запускает `std::jthread` обслуживания. Деструктор запрещает новые задачи обновления, останавливает maintenance thread, дожидается сохранённых `std::future<void>` задач, затем закрывает Cache. Статическая природа Cache означает, что одновременные независимые экземпляры Core с разными mapping в одном процессе не поддерживаются.

| Публичный метод | Контракт реализации |
| --- | --- |
| `initialize()` | Открывает или создаёт кеш; при повторном вызове после успеха возвращает `true`. Запускает maintenance thread. |
| `getAnime(alias_or_id, need_videos)` | Синхронно запрашивает API и создаёт новую shared Anime-запись; возвращает `expected<HeapHandle, ApiError>`. Caller release-ит handle. |
| `getAnime(anime_id, callback)` | Быстро возвращает shared slot либо `nullptr`; при необходимости запускает async обновление. Callback принимает `(id, Anime*)`, null указывает на неуспех. |
| `animeNeedsRefresh(id)` / `animeIsLoaded(id)` | Process-local статусы: требуется ли запрос и завершалась ли полная загрузка в текущем Core. |
| `searchTitles(params, callback)` | Возвращает false, если фоновой задаче не удалось стартовать; иначе true означает только принятие задачи. Callback получает параметры страницы и `SharedSearch*`/null; его bool управляет пагинацией Core. |
| `searchPageNeedsRefresh(params)` | Проверяет TTL точного page key; cache miss возвращает false. |
| `resolveSearch(handle)` / `releaseSearch(handle)` | Разрешает страницу с обновлением last-used либо удаляет всю цепочку от root. |
| `getFeed(watches, callback)` | Ставит задачу получения/обновления; callback получает watches и `SharedFeed*`/null. |
| `feedNeedsRefresh(watches)` | Проверяет только существующую запись process cache; miss возвращает false. |
| `resolveFeed(handle)` / `releaseFeed(handle)` | Разрешает Feed record либо освобождает Feed и Anime references внутри него. |
| `resolveAnime(handle)` / `releaseAnime(handle)` | Разрешает Anime pointer с touch времени либо снимает ownership reference. |
| `releaseAnime(Anime*)` | Находит указатель в `anime_by_id_` и снимает привязанную к entry ссылку; для произвольного handle используйте handle overload. |

Async callbacks выполняются вне UI/main thread и должны быть потокобезопасны. Core ловит исключения Anime callbacks; пользовательскому коду не следует рассчитывать на конкретный thread ID. В текущем `searchTitles` исключение callback для stale страницы приводит к освобождению этой страницы и остановке задачи; исключение callback для свежей страницы просто завершает worker и может оставить page/цепочку выделенной. Публичные callbacks поэтому не должны бросать исключения; при использовании Core напрямую оберните пользовательскую обработку внутри callback в собственный try/catch.

### Получение аниме

Синхронная перегрузка `getAnime(string_view, need_videos)` напрямую вызывает API, выделяет новую Anime-запись и сохраняет полный результат. Она возвращает `Result<HeapHandle>`, поэтому ошибка API или размещения передаётся как `unexpected(ApiError)`.

Асинхронная перегрузка `getAnime(int64_t, callback)` предназначена для быстрого ответа клиенту. Под mutex она ищет локальную `AnimeEntry` по ID; первый запрос создаёт shared slot и ставит обновление, следующий запрос получает retained reference на существующий slot. `AnimeEntry` хранит handle, состояние `updating`, признак `loaded_full`, время последнего API вызова и ожидающие callbacks. Если обновление уже выполняется, callback добавляется к нему; новая API-задача на тот же ID не создаётся. Иначе, если с прошлого API-запроса прошло больше пяти минут, запускается `std::async(std::launch::async, ...)`.

Worker фиксирует время непосредственно перед API-запросом, получает полную модель через `getAnimeAsync`, строит временный `Anime replacement`, затем освобождает старые переменные данные и копирует payload в тот же слот. При этом сохраняются usage count, last-used и идентичность handle. Callbacks вызываются после снятия mutex, каждый в try/catch, чтобы ошибка одного callback не остановила остальных. При ошибке API/конвертации/записи callback получает `nullptr`. Возвращённый из Core слот принадлежит вызывающему коду; в сценарии Server владение передаётся как handle.

Callback вызывается только когда запрос присоединился к уже выполняющемуся обновлению или инициировал новое. Если полная запись уже есть и прошло не более пяти минут, функция возвращает Anime pointer синхронно, но переданный callback не вызывается. Если слот был создан в Search/Feed и Core не имеет активной полной записи для него, первый detail-запрос обычно запускает API-запрос независимо от того, насколько недавно был разрешён сам shared slot.

`animeNeedsRefresh()` отвечает true для неизвестного Core ID, для активного update и для истёкшего TTL. При этом server вычисляет `refreshing` до вызова `getAnime`, поэтому флаг в немедленном ответе отражает состояние до запуска нового запроса. Для неизвестного ID он будет true. Для Search/Feed `*NeedsRefresh()` возвращает true только для уже существующей устаревшей записи; cache miss вернёт false, хотя сам `getSearch`/`getFeed` после этого начнёт API-запрос. Следовательно, эти флаги прежде всего показывают stale обновление, а не являются универсальным индикатором наличия сетевой задачи.

Есть тонкость текущей реализации: флаг `loaded_full` устанавливается при успешном обновлении и используется в ответном статусе сервера. Процессная карта `anime_by_id_` и timestamps пропадают при рестарте; shared-memory Anime record при этом может остаться. Если карта Core пуста, сервер считает запись требующей обновления и создаёт/получает слот по ID.

### Search

`Core::searchTitles(params, callback)` возвращается после постановки фоновой задачи. Задача начинает с `max(0, params.offset)` и для каждой страницы фиксирует `limit=10`, формирует ключ JSON-массивом всех фильтров в стабильном порядке, включая offset/limit. Значение `search_cache_` — исходный `vector<SearchResult>` и время запроса, хранится только в RAM процесса.

Для свежего кеш-ключа API не вызывается; из сохранённых моделей формируется новая shared page. Для устаревшего ключа старая страница сначала материализуется в SearchHeap и передаётся callback, затем запускается API обновление. Timestamp обновляется в момент обращения к API, а не просто при чтении кеша. При успешном API-ответе актуализируется process cache, строится новая shared page и вызывается callback второй раз. На cache miss запрос API выполняется до первого callback. Ошибка возвращает callback с `nullptr`.

Каждая shared page включает до десяти результатов. Anime-слоты находятся через `find_or_create_anime`; только что созданные слоты получают поля из SearchResult, уже существующие записи повторно не перезаписываются частичной моделью. SearchHeap удерживает Anime ссылкой. Callback возвращает bool: `true` — Core увеличивает offset на 10 и запрашивает следующую страницу; `false` завершает цепочку. Пагинация прекращается также при ответе меньше 10 элементов или переполнении offset. `searchPageNeedsRefresh()` нормализует offset/limit тем же способом и сообщает устаревание только для уже закешированного ключа.

IPC специально использует callback, который возвращает `false`: один `getSearch` выдаёт одну страницу, а клиент самостоятельно отправляет следующий запрос с offset+10. Обратите внимание: при stale refresh callback может вызываться для старой и новой страницы; клиенты должны освободить handle старого результата после переключения на новый.

### Feed

`getFeed(watches, callback)` также работает в фоновой задаче. Ключ кеша — JSON-представление вектора watches, а значение — модель `FeedResponse` в памяти Core. Свежий результат преобразуется в новый SharedFeed без API-запроса. Устаревший сначала преобразуется и передаётся callback, после чего Core запрашивает API; новый FeedResponse кешируется и превращается в другой SharedFeed. При отсутствии кеша сначала выполняется API. Ошибка запроса или размещения передаёт `nullptr`.

При создании Feed для каждой группы элементов выделяются/переиспользуются Anime slots. Поля отображаются из разных feed-моделей подходящими функциями преобразования; каждый список добавляет Anime handle через `FeedHeap::append_anime`, который удерживает ссылку. `getFeed()` не переиспользует один и тот же SharedFeed handle на повторных запросах: он строит новый снимок, а клиент обязан освободить предыдущий. Process cache Search/Feed и timestamps чистятся от старых ключей при успешном новом API-запросе, но это не персистентное хранилище.

### Фоновая очистка

Поток обслуживания ждёт пять минут между проходами. Затем cutoff вычисляется как `steady_clock::now() - 20 min`. SearchHeap удаляет устаревшие Search root chains; Cache выбирает по одной самой старой нулевой Anime-ссылке за итерацию и удаляет до cutoff. Активные ссылки препятствуют удалению независимо от возраста. Само получение Anime через `resolve_anime`, retain/release, обращение к Search обновляет метки последнего использования. Feed не входит в отдельный TTL cleanup: он живёт до `deleteFeed`/освобождения владельцем, при котором освобождаются связанные ссылки.

## Владение по шагам и поведение ошибок

### Жизненный цикл handles

Пример Anime через IPC:

1. Клиент отправляет `getAnime` с ID.
2. Core берёт или создаёт Anime slot, удерживает ссылку для вызывающей стороны и при необходимости ставит обновление.
3. IPC отвечает сразу с `{handle, loaded, refreshing}`. При первой загрузке содержимое может быть пустым или частичным из search/feed.
4. Фоновая задача получает API-ответ и обновляет тот же слот. Handle сохраняется, но строки и векторы в VariableHeap могут быть заменены.
5. Клиент получает `anime.updated`; при чтении записи после этого события он видит завершённое обновление. Межпроцессного read/write snapshot API у Anime нет.
6. После окончания использования клиент вызывает `deleteAnime`. Это release своей ссылки, а не команда безусловного физического удаления записи.

Search и Feed обновляются иначе: результат обычно строится как новый shared snapshot с новым handle. Клиент переключает читателей на новый handle и освобождает предыдущий. Anime handles внутри Search/Feed удерживаются контейнером; клиенту не нужно отдельно удалять их, если он не получил собственный handle через `getAnime`.

Handle является владением, а не только адресом. При передаче между компонентами одного процесса нужно явно передавать ответственность за release. Текущий IPC не имеет команды retain для клиента: один выданный handle следует освободить ровно один раз. Сервер не отслеживает handles по IPC-сессиям и не освобождает их автоматически при отключении клиента; забытые references могут удерживать Anime от очистки.

### Ошибки по слоям

- `Core::initialize()` возвращает `false`, если не получилось открыть или создать все четыре heaps.
- Невалидный/нулевой ID в async `getAnime` или ошибка выделения слота возвращает `nullptr` без успешного обновления.
- В Anime callback `nullptr` означает, что API-запрос либо запись результата завершились неуспешно. Текст `ApiError` через этот callback не передаётся. Синхронный overload возвращает `Result<HeapHandle>` и сохраняет ошибку API.
- Search/Feed callback передаёт `nullptr` при ошибке API или размещения shared data. При stale-ответе старое значение уже могло прийти до ошибки обновления.
- Невалидный JSON IPC, неправильные типы полей, неизвестный метод и неверный handle возвращаются клиенту как `ok:false` с текстом `error`.
- При частичном построении объектов пути очистки обязаны освободить уже созданные SharedString/SharedVector и references. При добавлении раннего выхода проверьте ownership каждого промежуточного объекта.

Асинхронный IPC сейчас не имеет cancellation token, отдельной передачи подробного `ApiError` и client session/lease для автоматического освобождения handles. Эти функции потребуют расширить контракты Core/Server и согласовать версию протокола.

## Точные ключи и правила TTL

Core использует `steady_clock`: интервалы не сдвигаются при ручной коррекции календарных часов. Значения `last_used_ns` в shared memory сравнимы процессами на одной работающей системе, но не являются UTC timestamp и не предназначены для трактовки после перезагрузки.

| Данные | Ключ/время | Поведение |
| --- | --- | --- |
| Async Anime | ID в локальной `anime_by_id_`; `last_api_request` в `AnimeEntry`. | Пока `now - last_api_request <= 5 min`, API не вызывается. Время устанавливается перед самим API вызовом. Если запись обновляется, новый callback присоединяется к текущей задаче. |
| Search page | JSON-массив всех фильтров SearchInput в фиксированном порядке, с нормализованными `offset` и `limit`. | До 5 минут — cached result без API. Старее — stale result сразу, затем API. Совпадает только точный ключ страницы. |
| Feed response | JSON-кодирование массива `watches`, порядок элементов сохраняется. | До 5 минут — cached response. Старее — старый результат, затем обновление. Перестановка watches даёт другой ключ. |
| Anime slot | `last_used_ns` обновляется операциями Cache. | Физическое удаление — только при нулевом usage count и времени старше 20 минут. |
| Search chain | У каждой страницы свой last-used; разрешение страницы обновляет её и root. | Удаляется вся цепочка, только если самое позднее время использования всех страниц старше 20 минут. |

Search и Feed API-модели кешируются только в памяти процесса Core. Несколько процессов могут совместно читать и удерживать shared records, но их process-local карты TTL не разделяются. После перезапуска сохраняемые heaps не восстанавливают сами по себе время свежести API-ответа.
