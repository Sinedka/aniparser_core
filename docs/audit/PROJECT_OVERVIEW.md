## Назначение

Aniparser Core — локальный сервер каталога аниме: поиск, главная лента,
подробности, получение ссылок видеопотоков, история, избранное, статусы
просмотра и прогресс эпизода. Данные каталога приходят из yani.tv; Kodik и
Aksor разбирают iframe, AniLibria получает серии отдельным запросом по alias.
Воспроизведение видео не реализовано: TUI показывает и копирует URL.

Исходники — C++23; конфигурация — CMake 3.25+, Nix flake, direnv.
JSON-схема моделей задаётся макросами в `models.def` (56 структур), а не
вручную продублированными рабочими объявлениями. CPR использует libcurl.
Clipboard запускает внешние программы через `posix_spawnp`, без shell.

## Основные пути выполнения

1. **Запуск сервера:** Core загружает `history.json`, создаётся Server, затем
   IpcServer. Unix слушает сокет, Windows — named pipe. Главный поток ждёт
   SIGINT/SIGTERM. Завершение идёт в обратном порядке; Core явно join-ит пул.
2. **Anime/Search/Feed:** IPC → Server → Core; сначала callback со снимком,
   затем при необходимости задача в пуле 4/128 → HTTP → обновление кэша →
   callback с событием. TTL — пять минут. Anime/Search/Feed — ожидание одного
   обновления, а не бесконечная push-подписка с таймером.
3. **Коллекции:** изменение под `Core::mutex_`, снимок состояния, запись через
   SaveManager, уведомления. История и избранное независимы; четыре статуса
   взаимоисключающие. Каждый список ограничен 1000 ID.
4. **Страница коллекции:** немедленный snapshot, затем Search по ID для
   устаревших карточек. Отрицательный кэш отсутствующих ID — пять минут.
5. **Видео:** IPC синхронно вызывает API-провайдер. Kodik делает до трёх
   последовательных HTTP-запросов. AniLibria сначала запрашивает yani.tv,
   затем основной/резервный API. Этот путь обходит Core-кэш и TaskPool.
6. **TUI:** `hello` → история → Feed; поиск/детали/плеер/озвучка/серии/качество.
   Запросы синхронные, обновления читаются в цикле UI; clipboard получает URL
   через stdin. Экран истории и редактирование коллекций не реализованы.

## Контракты

- API: `yani::Result<T> = std::expected<T, ApiError>`; ошибка имеет status,
  message, data. Есть синхронные и future-варианты. Core использует синхронные
  вызовы в своём пуле. Ожидаемая ошибка и исключение — разные механизмы;
  текущие исключительные пути покрыты неравномерно.
- Core: callbacks получают owning values, вызываются вне `mutex_`. Это не
  означает отсутствие других удерживаемых locks — см. AUD-002.
- Кэш: страницы Search содержат порядок ID, AnimeCache владеет карточками.
  Partial и full имеют разные правила обновления, сейчас с противоречиями.
- IPC: JSON Lines, версия 3; ответ и события повторяют request ID. Anime
  меняет `videos` на `players → dubbers → episodes`. Полные JSON-значения не
  содержат адресов серверной памяти. Входной буфер сервера ограничен 1 MiB.
- Коллекции: snapshot имеет revision, sequence, refreshing, reason. Статусы:
  0 — нет, 1 — planned, 2 — watched, 3 — completed, 5 — dropped.
- Хранилище: читатель версий 1–4, писатель версии 4; временный файл рядом с
  основным, затем rename/MoveFileExW. Один каталог предназначен для одного
  серверного процесса; межпроцессной блокировки нет.

## Состояние и оценка

Базовое разделение слоёв разумное; owning values, `unique_ptr`, mutex Core,
coalescing и явное завершение workers уже снижают многие риски C++.
Перестраивать проект с нуля не требуется. Основные слабые места — гарантии
сохранения, обратные вызовы под дополнительными locks, блокирующий IPC,
переходы состояний TUI и несовместимые правила свежести/отсутствующих полей.
