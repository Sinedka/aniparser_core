## AUD-001 — ошибка диска скрывается успешным ответом

**High · Confirmed · E.** Файлы: `src/core/history.cpp:7–66`, `:250–285`,
`:443–490`; `src/server/ipc/unix.cpp:846–864`, Windows `:829–847`.

**Описание и причина.** Мутации сначала меняют память, затем вызывают
`saveState`. Результат записи только логируется, метод возвращает true.
IPC отправляет `ok:true`, а в случае progress — «сохранённый» объект.

**Сценарий и последствия.** `ANIPARSER_DATA_DIR` указывает на обычный файл.
`updateAnimeSaveData(42, Kodik, Dub, 1, 10)` отвечает успехом; чтение в том же
процессе видит прогресс; после перезапуска приходит null. Это воспроизведено
через настоящий Unix IPC в `out/audit-f2jw1dxq/ipc.log`. Аналогично действуют
заполненный диск, ошибки прав и rename. Пользователь теряет подтверждённые данные.

**Минимальное исправление.** Возвращать различимый storage error до отправки
успеха. Явно выбрать семантику: rollback либо «изменено в памяти, не сохранено»
с dirty-state/retry. Просто `return saved` не откатывает мутацию и не решает
согласование revisions/событий. Закрепить выбранный контракт для обоих transport-ов.

**Проверка.** Ошибка create/open/write/rename, затем восстановление диска,
повтор операции и перезапуск. Проверять и ответ, и файл, и notifications.

## AUD-002 — повторная мутация из callback блокирует Core

**High · Confirmed · B.** `src/core/history.cpp:9–23`, `:207–214`,
`:252–266`, `:409–415`, `:447–469`, `:622–628`.

**Описание и причина.** `collection_save_mutex_` остаётся захваченным при
`notify_*`, а notify вызывает пользовательский callback. Повторная операция
записи в callback пытается захватить тот же нерекурсивный mutex.

**Сценарий.** На пустом Core подписаться на favorites; в callback при
`updated=true` вызвать `removeFavorite(1)`, затем снаружи вызвать
`addFavorite(1)`. Тест с реальными библиотеками не завершился за 2 секунды;
дочерний процесс остановлен timeout-ом. Сеть для этого сценария не нужна.

```cpp
// Текущий опасный порядок:
std::unique_lock lock(collection_save_mutex_);
save();
callback(); // callback -> removeFavorite -> тот же mutex

// Требуемый принцип, не готовый патч:
{ std::unique_lock lock(collection_save_mutex_); save(); prepare_events(); }
dispatch_events_in_order(); // вне locks, с сохранением порядка событий
```

**Последствия.** Зависает операция и остальные записи коллекций. Даже без
reentrancy медленный IPC callback задерживает все мутации.

**Исправление.** Подготовить owning notifications в сериализованной операции,
освободить locks перед вызовом; сохранить порядок revisions/sequence отдельным
порядком dispatch. Не заменять mutex на recursive_mutex как основное решение.
**Проверка.** Reentrant callback, callback с исключением, параллельные мутации,
монотонность sequence и отсутствие старого состояния после нового.

## AUD-003 — медленный клиент способен заблокировать остановку

**High · Confirmed · B.** Unix `src/server/ipc/unix.cpp:110–145`, `:413–425`;
Windows `src/server/ipc/windows.cpp:118–146`, `:390–403`.

**Причина.** Блокирующий send/WriteFile выполняется под write mutex. `interrupt`
пытается сначала захватить тот же mutex, чтобы прервать I/O. Операция,
необходимая для разблокирования записи, ждёт завершения этой записи.

**Сценарий.** Клиент перестаёт читать, сервер заполняет его выходной буфер;
send держит lock. SIGTERM приводит stop к `client->interrupt()`, где он ждёт
lock бесконечно. При рассылке callback может быть занят и API worker. Цепочка
подтверждается кодом; нагрузочный запуск не выполнялся.

**Последствия.** Зависание stop, а при коллекциях — всех записей через AUD-002.
**Исправление.** Ввести ограничение времени/объёма отправки и путь отмены,
который не ждёт lock заблокированной записи. Сохранить защиту от fd reuse;
просто убрать mutex вокруг close небезопасно. Для Windows отдельно определить
отмену синхронного I/O и завершение worker.
**Проверка.** Клиент с малым receive buffer и без чтения; deadline stop,
разрыв соединения во время отправки, несколько клиентов, ASan/TSan.

## AUD-004 — конкурентное чтение и запись listener

**High · Confirmed · B.** `src/server/ipc/unix.cpp:379`, `:413–419`, `:431–434`.

**Описание.** `listener` — обычный int. stop пишет `-1`, accept thread читает
его в `accept(listener, ...)`. Atomic stopping не защищает int: поток мог
прочитать false до того, как stop изменит listener.

**Сценарий.** accept loop проходит проверку while; stop закрывает fd и пишет
-1 одновременно с вычислением аргумента accept. Это data race по правилам
C++, то есть undefined behavior; конкретный crash не утверждается.
**Исправление.** Не изменять переменную listener до join; accept thread должен
использовать стабильное значение дескриптора. Отдельно организовать wakeup
и закрытие так, чтобы избежать reuse закрытого fd.
**Проверка.** Многократные start/stop и подключения под TSan, в том числе
остановка между проверкой stopping и accept. TSan в этом аудите не запускался.

## AUD-005 — текущий Windows-транспорт не компилируется

**High · Confirmed · A.** `src/server/ipc/windows.cpp:93–98`, `:527–792`.

**Причина.** В файле определены JSON helpers `success` и `failure`, но новые
обработчики Favorites/статусов вызывают `ok(id)` и `error(id, ...)` из Unix
варианта. Объявлений этих helpers в Windows translation unit нет.

**Сценарий.** Сборка `server_ipc` на Windows компилирует эти обработчики,
включая `auto reply = ok(id)` на строке 527. Получаем unresolved identifier
на этапе компиляции. Подтверждено исходниками, Windows-компилятор не запускался.
Linux-сборка вообще не компилирует windows.cpp.

**Последствия.** Нельзя собрать сервер на заявленной платформе.
**Исправление.** Согласовать вызовы с локальными `success/failure`, без
изменения wire JSON; затем действительно собрать Windows. Это не доказывает,
что других Windows compile/runtime ошибок нет.
**Проверка.** MSVC/MinGW build, затем hello, favorites, четыре статуса,
ошибочные запросы и disconnect cleanup.

## AUD-006 — завершённые соединения не освобождают записи и threads

**High · Confirmed · B.** Unix `src/server/ipc/unix.cpp:382–383`, `:440–443`,
`:447–489`; Windows `src/server/ipc/windows.cpp:368–369`, `:427–430`, `:434–477`.

**Причина.** Каждый accept добавляет shared_ptr Client и joinable thread в
векторы. client_loop закрывает ресурс, но ничего не удаляет из этих векторов.
Join/clear выполняются только при stop всего сервера.

**Сценарий.** Клиент многократно подключается, делает hello и отключается.
Число активных клиентов почти нулевое, а размер векторов растёт с общим числом
подключений за жизнь процесса. Это удержание ресурсов, не утечка открытых
socket fd: fd закрываются. Лимита одновременно активных клиентов также нет.

**Последствия.** Рост памяти/ресурсов threads; `std::thread` при исчерпании
ресурсов может бросить в accept thread, где нет catch, и завершить процесс.
**Исправление.** Собирать завершённые workers, join-ить вне `clients_mutex`,
удалять Client после очистки; ограничить активные соединения. Ошибку создания
worker обработать с закрытием принятого дескриптора.
**Проверка.** Тысячи последовательных и ограниченное число параллельных
подключений; стабильные RSS/fd/thread resources, корректный stop.

## AUD-007 — отсутствующее поле стирает полезные данные sentinel-ом

**Medium · Confirmed · F.** `src/api/json.hpp:23–28`, `:44–46`;
`src/core/cache/anime_cache.cpp:10–27`, `:143–159`, `:291–295`.

**Причина.** Missing/null int64 преобразуется в INT64_MIN, double — в -1.
Merge считает любое ненулевое число полезным. Информация «поля нет» уже
потеряна, и sentinel затирает настоящее число.

**Воспроизведение.** Сохранить SearchResult ID=1, year=2020. Разобрать JSON
`{"anime_id":1,"title":"partial"}` и сохранить как другой SearchResult.
В реальном AnimeCache год стал `-9223372036854775808`. Для вложенного объекта
с присутствующим `rating:{}` аналогичный риск есть у -1 average.

**Последствия.** Неверные карточки и выдача sentinel клиентам.
**Исправление.** Минимально исключить documented sentinels из partial merge
для соответствующих полей. Лучше позже сохранять presence отдельно. Глобально
заменять missing на 0 нельзя без проверки остальных контрактов.
**Проверка.** Missing/null/0/валидное значение для чисел верхнего уровня и
вложенных объектов; значения после JSON round-trip и нескольких partial merges.

## AUD-008 — свежие поля Search не обновляют ранее полную карточку

**Medium · Confirmed · F.** `src/core/cache/anime_cache.cpp:143–175`;
`src/core/search_feed.cpp:143`, `:202–214`.

**Причина.** После первого full refresh `has_full_details` навсегда запрещает
merge данных Search/Feed, но `card_refreshed_at` всё равно обновляется.
Свежий callback Search отдаёт сырой API result, следующий snapshot — старый кэш.

**Воспроизведение.** `finishRefresh(2, full{title="old",year=2020})`, затем
`storeSearchResults(...,{id=2,title="new",year=2026})`. Реальный
`searchResults({2})` вернул old/2020. Проверено C++ probe. Правило действует и
после истечения TTL full-card, если её отдельно не перезагружать.

**Последствия.** Пользователь видит возврат к старым сведениям; страницы
коллекций могут бесконечно освежать timestamp без обновления содержимого.
**Исправление.** Разрешить обновление общих полей у full-card без удаления
details/videos; timestamps должны отражать реально обновлённые поля.
**Проверка.** Full → новый Search → повторный snapshot, Feed и история;
не потерять уникальные details и порядок ID.

## AUD-009 — need_videos не входит в критерий полноты

**Medium · Confirmed · F.** `src/core/anime_service.cpp:24–44`;
`src/core/cache/anime_cache.cpp:56–74`, `:118–121`.

**Причина.** `subscribeAnime(..., false)` и `(..., true)` используют одну
запись с одной свежестью и одну общую задачу. Любой успех отмечается как full.

**Сценарий.** C++-потребитель Core сначала получает Anime без видео, затем
в течение пяти минут запрашивает видео. Второй вызов не инициирует refresh;
если запросы параллельны, первый false определяет результат обоим.
Текущий Server всегда передаёт true, поэтому обычный IPC-путь сам этот сценарий
не создаёт; проблема публичного Core API, не всех IPC-запросов.

**Исправление.** Отслеживать загруженность/свежесть videos отдельно либо
убрать переключатель и всегда загружать videos, если это приемлемо для API.
**Проверка.** false→true, true→false, параллельное coalescing и ошибка
дополнительной загрузки без потери прежних данных.

## AUD-010 — исключение первого callback оставляет запись без задачи

**Medium · Confirmed · B.** `src/core/anime_service.cpp:36–44`;
`src/core/search_feed.cpp:149–159`, `:243–252`.

**Причина.** Флаг updating и callback регистрируются до первого синхронного
callback. Сам callback не защищён try/catch; submit стоит после него.

**Сценарий.** На холодном кэше callback бросает runtime_error. subscribe
прерывается до submit. Следующий запрос видит updating и присоединяется к
несуществующей задаче. IPC ловит исключение снаружи, но флаг Core не сбрасывает.
Сбой сериализации/отправки первого snapshot тоже может бросить исключение.

**Последствия.** Anime ID/Search key/Feed больше не обновляется до рестарта.
**Исправление.** Изолировать исключение callback и гарантировать запуск либо
rollback регистрации/флага через scope guard. Аналогично проверить initial
callbacks коллекций, чтобы не оставлять недоступный вызывающему subscription ID.
**Проверка.** Бросающий initial callback, затем обычный subscriber того же
ключа; он должен получить завершение, а флаг не должен остаться навсегда.

## AUD-011 — ошибка Search/Feed не завершает протокольное ожидание

**Medium · Design concern · C.** `src/core/search_feed.cpp:205–215`, `:269–275`;
`src/server/ipc/unix.cpp:904–944` и соответствующие Windows handlers.

**Описание.** Начальный ответ говорит refreshing=true, но при API error
callbacks удаляются без error event. Активный stream ID IPC остаётся до
unsubscribe/disconnect. Это уже описано в документации, не скрытый баг
обещанного error event.

**Сценарий и последствия.** API timeout при первом поиске оставляет UI на
«refreshing» без результата; повторные запросы с новыми IDs накапливают
неоконченные streams. Нет различия «ещё работает» и «уже неуспешно завершено».
**Исправление.** Определить terminal error для Search/Feed и metadata refresh,
очищать stream при любом завершении; согласовать оба транспорта и клиентов.
**Проверка.** Timeout/HTTP error/invalid JSON, успешная повторная попытка,
unsubscribe и отсутствие вечного refreshing. До изменения клиенты должны
иметь собственный deadline.

## AUD-012 — тип и диапазон числовых полей IPC проверяются неполно

**Medium · Confirmed · E.** Unix `src/server/ipc/unix.cpp:510–512`, `:609`,
`:850–855`; Windows `src/server/ipc/windows.cpp:480–482`, `:605`, `:831–836`;
аналогичные операции и `parse_search` в обоих файлах.

**Причина.** `get<int64_t>`/`value<size_t>` — преобразование JSON, не проверка
«пришло целое неотрицательное число допустимого диапазона».
**Воспроизведение.** Через IPC `addPlanned` с anime_id=42.9 добавил ID 42.
`subscribeHistory` с offset=-1, limit=-1 вернул offset=18446744073709551615,
limit=50. На этой машине size_t — 64-bit. Диапазоны Search также не ограничены.

**Последствия.** Операция над другим ID, неожиданные страницы, лишняя работа.
Для некоторых выходящих за диапазон floating-point→integer преобразований
дополнительно требуется проверка санитайзером; такой runtime случай не тестировался.
**Исправление.** Проверять integer type и диапазон до get; limit/offset/IDs
валидировать единообразно, задав явные границы протокола. Float ID отклонять.
**Проверка.** -1, 0, 1, 1.5, int64 max, uint64 max, 1e100, string/null/array;
ошибочный запрос не должен менять коллекции.

## AUD-013 — Backspace оставляет начальный байт UTF-8

**Medium · Confirmed · A.** `tui/tui_app.cpp:129–135`, `:283–286`.

**Причина.** Сначала удаляется последний байт, затем continuation bytes,
но не начальный байт многобайтного символа.
**Сценарий.** «я» = D1 8F. После pop_back остаётся D1; while его не удаляет.
Полученная строка невалидна. `Json(query).dump()` может бросить до запуска
поиска, в search_prompt этот вызов вне catch метода search.
**Последствия.** Испорченный запрос либо выход TUI при обычном русском вводе.

**Минимальный принцип исправления** для уже валидного UTF-8:

```cpp
// Найти начало последнего code point, затем удалить весь суффикс.
auto pos = text.size();
if (pos != 0) {
  --pos;
  while (pos > 0 && (static_cast<unsigned char>(text[pos]) & 0xc0) == 0x80)
    --pos;
  text.erase(pos);
}
```

Это удаление code point, не целой графемы с combining marks.
**Проверка.** ASCII, кириллица, emoji, смешанная строка, пустая строка,
последовательные Backspace; после каждого шага валидный UTF-8/JSON.

## AUD-014 — холодный null snapshot не проходит в экран деталей

**Medium · Confirmed · A.** `tui/tui_app.cpp:264–267`, `:319–355`.

**Причина.** `reply.value("anime", object())` возвращает null, если ключ
присутствует и равен null. update_anime сохраняет null и вызывает
build_players → `detail_.value("players", ...)`, что бросает type_error.
`detail_id_` и Screen::Details задаются только после этого вызова.

**Сценарий.** Открыть ID, отсутствующий в AnimeCache, например ещё не
кэшированный элемент viewing_order. IPC документированно возвращает
`anime:null, refreshing:true`. TUI остаётся на прежнем экране, detail_id не
обновляется. Позднее событие обновляет модель, но не выполняет пропущенный
переход экрана. На обычных строках Feed/Search partial карточка часто уже
есть, поэтому дефект проявляется не при каждом открытии.

**Исправление.** Представлять loading явно; не вызывать object accessors на
null. Установить ID/состояние экрана независимо от наличия snapshot, безопасно
рисовать loading. **Проверка.** Cold null→success, null→error, partial→full,
уход с экрана до результата, открытие следующего Anime.

## AUD-015 — выбранный индекс перестаёт соответствовать новому меню

**High · Confirmed · B.** `tui/tui_app.cpp:338–357`, `:380–393`, `:429–430`,
`:532–558`, `:573–594`.

**Причина.** anime.updated полностью пересоздаёт players/dubbers. В конце
pump_events корректируется только selected_; player_index_ и dubber_index_
не восстанавливаются. activate на Players использует `players_[index]` без
проверки пустого меню. load_anilibria_episodes тоже индексирует напрямую.

**Сценарий.** В меню Players аниме A открыть `/`, найти и открыть аниме B без
поддержанных плееров. Esc вернёт в Search, следующий Esc восстановит сохранённый
экран Players аниме A, но players_ уже принадлежит B и пуст. Enter читает
`players_[0]`. Если у B плееры есть, восстановленный selected_ может превышать
их число. go_back восстанавливает экран/индекс без модели и проверки границ;
clamp в pump_events выполняется только при наличии событий. Дополнительно
refresh пересоздаёт меню, не восстанавливая player_index_/dubber_index_.
Объектные обращения при размере 0 — UB, даже если capacity вектора ещё не
обнулена. Пустой full-update сам по себе сейчас маскируется AUD-025, поэтому
не используется здесь как самостоятельное доказательство выхода за границу.

**Последствия.** Crash/некорректный доступ к памяти либо выбор другой озвучки.
Локальность TUI не даёт оснований объявлять это Critical/доказанным exploit.
**Исправление.** После замены данных валидировать всю цепочку индексов;
сохранять выбор по устойчивым именам/ID либо возвращать на безопасный экран.
Все действия должны проверять empty/границы непосредственно перед доступом.
**Проверка.** Обновить список на каждом экране: shrink, empty, reorder,
удаление выбранной озвучки; ASan и debug STL плюс ручной Enter/Esc.

## AUD-016 — Notcurses не защищён RAII

**Medium · Confirmed · B.** `tui/tui_app.cpp:832–841`.

**Причина.** notcurses_stop вызывается только в нормальном пути после run.
Исключение из initialize/pump_events/draw перескакивает прямо в catch.
**Сценарий.** После успешного notcurses_init сервер закрывает соединение
во время initialize или приходит некорректный JSON. Терминальный context не
останавливается; процесс возвращает 1 с потенциально испорченным режимом TTY.
ОС освободит память процесса, но режим терминала сам по себе этим не исправлен.
**Исправление.** unique_ptr с custom deleter/notcurses_stop либо scope guard
сразу после init. Не полагаться на catch в каждом отдельном методе UI.
**Проверка.** Исключения после init на разных стадиях и восстановление
терминала; normal exit/q тоже вызывает stop ровно один раз.

## AUD-017 — UI ждёт IPC без срока и не замечает EOF при polling

**Medium · Design concern · C.** `tui/ipc_client.hpp:44–63`, `:72–77`, `:90–101`;
`tui/tui_app.cpp:409–410`, `:454–455`.

**Описание.** request/send/recv блокируют единственный UI thread без
deadline. poll_messages игнорирует POLLHUP/POLLERR и recv==0, fd остаётся
«подключённым». input_/inbox_ не имеют лимита.
**Сценарий и последствия.** Сервер принял соединение, но не ответил, либо
синхронный видеозапрос задержался: UI не обрабатывает q/resize. Если сервер
исчез без нового request, интерфейс может продолжать выглядеть подключённым.
Лимит 1 MiB серверного request buffer не ограничивает клиентские ответы.
**Исправление.** Для начала poll с deadline и явное disconnected state;
проверять EOF/errors, ограничить входной буфер. В дальнейшем неблокирующие
requests в текущем цикле UI, без обязательного нового thread pool.
**Проверка.** Mock server: молчит, закрывает соединение, присылает строку
частями, события до ответа, чрезмерный ответ; UI сохраняет управление.

## AUD-018 — повреждённый/неподдержанный файл затем перезаписывается

**High · Confirmed · E.** `src/core/cache/save_manager.cpp:64–80`, `:151–158`,
`:200–245`; `src/core/core.cpp:7–9`; мутации `src/core/history.cpp:7–23`.

**Причина.** loadState возвращает одинаковое пустое PersistentState и при
отсутствии файла, и при parse/I/O error, и при неизвестной версии. Core не
знает, что оригинал надо сохранить и запретить запись.
**Сценарий.** Запустить старый binary с корректным файлом будущей версии 5
или с повреждённым JSON; load вернёт пустые списки. Первый addHistory запишет
v4 поверх исходного файла. Даже если прежний файл можно было восстановить,
после rename его содержимого уже нет. Сценарий доказан потоком кода, отдельный
тест с перезаписью не выполнялся.
**Последствия.** Потеря коллекций/прогресса, особенно при downgrade.
**Исправление.** `loadState` должен различать missing, loaded, unsupported,
corrupt, I/O error. При ошибках не разрешать обычную перезапись; сохранить
оригинал/backup и показать понятную ошибку. Не удалять файл автоматически.
**Проверка.** Fixtures v1–4, v5, обрезанный JSON, неверные типы, отказ чтения;
после запуска и попытки мутации оригинальные байты остаются доступны.

## AUD-019 — атомарность записи не равна crash durability

**Medium · Design concern · E.** `src/core/cache/save_manager.cpp:205–245`.

**Описание и причина.** На Unix выполняется ostream.flush и rename, но нет
fsync временного файла и каталога. flush перемещает данные из C++-буфера в ОС,
а не обязательно на носитель. Atomic rename защищает читателя от частично
заменённого имени, но сам не является обещанием пережить отключение питания.
**Сценарий.** Питание исчезает после успешного ответа IPC. На части файловых
систем возможна потеря последнего сохранения; точное поведение зависит от FS.
В аудите power-loss не эмулировался, факт потери на этой машине не утверждается.
**Исправление.** Сначала определить требуемую гарантию. Если нужна durable
запись — flush/fsync file → rename → fsync parent с обработкой ошибок; проверить
close errors. Windows-путь оценить отдельно, не переносить Unix вывод буквально.
**Проверка.** Fault injection на каждом шаге и recovery на целевых FS; не
выдавать обычный process kill за полноценную проверку power loss.

## AUD-020 — постоянный прогресс может расти без ограничения

**Medium · Design concern · E.** `src/core/history.cpp:44–66`, `:126–136`;
`src/core/core.hpp:244`; `src/core/cache/save_manager.cpp:134–149`, `:187–193`.

**Описание.** Лимит 1000 применяется к ID коллекциям, но не к
anime_save_data_. Обновить прогресс можно для любого положительного ID;
удаление истории его намеренно не удаляет. В API нет отдельного удаления
save_data или лимита строк player/dubber/episode, кроме общего IPC request size.
**Сценарий.** Долгая эксплуатация/баг клиента добавляет тысячи разных ID.
Каждый новый progress переписывает и копирует весь накопленный map/JSON.
**Последствия.** Рост памяти, файла и задержки каждой записи; локальный
клиент способен усилить нагрузку. Это не утверждение утечки fd/памяти C++.
**Исправление.** Определить явный лимит/политику retention, операцию удаления
и разумные длины строк. Не связывать очистку молча с removeHistory: текущий
контракт допускает независимость прогресса от истории.
**Проверка.** Достижение границы, независимость от списков, рестарт, размер
и время сохранения, отсутствие внезапного удаления пользовательского прогресса.

## AUD-021 — транспортные реализации дублируют бизнес-маршрутизацию

**Low · Design concern · C.** `src/server/ipc/unix.cpp:492–994`;
`src/server/ipc/windows.cpp:479–974`.

**Описание.** Одинаковые validation, методы, callbacks, коллекции и JSON
продублированы в двух крупных handlers; шесть наборов subscription bookkeeping
повторяются также внутри Client. AUD-005 показывает уже возникший результат.
**Сценарий.** Добавить поле/команду в одном файле и забыть второй. Linux CI
соберёт только Unix и не заметит расхождение.
**Последствия.** Стоимость сопровождения и несовместимый wire contract.
**Исправление.** Сначала parity/compile проверки, затем небольшими шагами
общий dispatcher/serialization с независимыми transport adapters. Не делать
массовую абстракцию одновременно с исправлением locks.
**Проверка.** Один набор JSON fixtures для обеих платформ, ответы/ошибки,
unsubscribe/disconnect, subscriptions/revisions. Субъективное сокращение числа
строк не является критерием успеха.

## AUD-022 — src/api/test.cpp создаёт ложное впечатление тестового покрытия

**Low · Design concern · D.** `src/api/test.cpp:1–1456`;
`src/api/CMakeLists.txt:6–22`, `src/app/main.cpp:12–76`.

**Описание и причина.** Файл содержит самостоятельные дубликаты моделей и
JSON-конвертеров, не зарегистрирован ни в одной CMake-цели; тестового runner
или assert-сценариев в нём нет. Реальные offline checks находятся в my_app.
**Сценарий.** Разработчик исправляет test.cpp и ожидает изменения поведения
или расширения проверок — build вообще не использует файл.
**Последствия.** Путаница и устаревший альтернативный «справочник» схемы.
**Исправление.** Сначала явно документировать назначение legacy-файла;
в отдельной согласованной задаче решить его судьбу. Не подключать его к api:
дублирование определений создаст новую проблему. В этом аудите файл не удалён.
**Проверка.** Проверить список source targets; реальные regression cases
должны запускаться явной командой и падать при возвращении дефекта.

## AUD-023 — AniLibria превращает HTTP-ошибки в status=0

**Medium · Confirmed · F.** `src/api/anilibria.cpp:103–110`, `:179–189`;
`src/server/ipc/unix.cpp:968–975`; `docs/SERVER.md:115–117`.

**Причина.** request_release сохраняет status/data HTTP error, но внешний
fallback loop собирает только message. Если оба запроса неуспешны, итоговый
make_error вызывается с 0, даже если были HTTP 404/429/500.
**Сценарий.** Оба AniLibria хоста ответили JSON + HTTP 404. IPC отдаст status=0,
который документация описывает как случай без полученного HTTP-ответа.
**Последствия.** Клиент не отличит сетевой сбой от rate limit/отсутствующего
релиза; потеря диагностических данных.
**Исправление.** Сохранить ошибки попыток структурно, определить итоговый
status (например последней попытки) и передавать исходные HTTP сведения.
Не выполнять fallback на каждый вид ошибки без явного решения о политике.
**Проверка.** 404+404, timeout+500, 429+success, malformed JSON, проверка
status/message/data API и обоих IPC transport-ов на mock HTTP responses.

## AUD-024 — блокирующий submit из worker может остановить обработку очереди

**Medium · Confirmed · B.** `src/core/task_pool.cpp:32–53`, `:70–82`;
`src/core/history.cpp:212–216`, `:224–241`; `src/core/search_feed.cpp:212–215`.

**Причина.** submit ждёт места в bounded queue. Worker выполняет callbacks,
а те вправе вызвать subscribe/metadata refresh с новым submit в тот же пул.
Запрета или специального пути для worker submissions нет.
**Сценарий.** Для `TaskPool(1,1)` worker внутри задачи делает два submit:
первый заполняет очередь, второй ждёт места, но единственный потребитель —
он сам. Для 4 workers тот же цикл возможен при занятости всех четырёх.
shutdown может разбудить ожидающих submit, поэтому это остановка обработки
до внешнего shutdown, а не доказательство невозможности любого завершения.
Производственный сценарий насыщения всех четырёх не запускался.
**Последствия.** Новые запросы перестают исполняться, внешний submit тоже ждёт.
**Исправление.** Неблокирующее принятие с явной ошибкой перегрузки либо
отдельный безопасный путь для nested scheduling; не исполнять произвольную
задачу под mutex очереди. Важно обработать rejection и сброс updating.
**Проверка.** Детерминированный barrier-тест заполненной очереди, nested submit,
четыре callbacks одновременно, stop и корректное terminal уведомление.

## AUD-025 — полный Anime snapshot не удаляет исчезнувшие поля TUI

**Medium · Confirmed · A.** `tui/tui_app.cpp:55–73`, `:264–267`, `:577–578`.

**Причина.** Для anime.updated вызывается partial merge, игнорирующий
пустые массивы/строки/нули. Но updated Anime — полный snapshot, где пустое
значение может быть актуальным и должно заменить старое.
**Сценарий.** В cached Anime были players/genres/description. Новый полный
ответ содержит `players:[]` или пустую description. merge оставляет прежние
данные; TUI предлагает уже отсутствующие видео. Это отдельная проблема от
sentinel merge backend и не устраняется исправлением AUD-007.
**Исправление.** Успешный full update заменяет detail целиком; initial partial
и full явно различаются. Согласовать это с безопасным восстановлением выбора
в AUD-015. **Проверка.** Непустое→пустое для players, description, genres,
нулевые значения и metadata partial→full; UI должен отражать новый snapshot.

## Дополнительные ограничения, не объявленные подтверждёнными багами

- Windows `start()` возвращает true до CreateNamedPipe; cancellation
  синхронного I/O и `constexpr HANDLE kInvalid = INVALID_HANDLE_VALUE` требуют
  реальной проверки компилятором/на Windows. Это зафиксированные направления
  продолжения, не ещё три подсчитанных дефекта.
- На Unix без MSG_NOSIGNAL следует проверить SIGPIPE, EINTR и наследование fd
  процессами clipboard. Linux-путь MSG_NOSIGNAL есть; macOS не тестировалась.
- Права и race при создании endpoint в общем `/tmp`, default ACL Windows pipe,
  symlink/несколько процессов при `.tmp` persistence требуют threat model и
  платформенных проверок. Межпроцессная сохранность сейчас не обещана.
- CPR redirects, размер HTTP body, корректность прямых URL и совместимость
  с текущим HTML/JS провайдеров не проверены живыми запросами. SSRF/exploit
  не объявлены доказанными: whitelist исходного домена сам по себе не
  доказывает ни наличие, ни отсутствие проблем redirects.
- `request_async` вызывает parse_response до внутреннего try; исключения
  allocation/формирования error могут уйти в discarded CPR future и привести
  к broken_promise вместо Result. Это требует отдельного fault injection;
  обычная синтаксическая JSON-ошибка уже обрабатывается parse_response.
- Exception safety контейнеров при bad_alloc и copy классов с fd/iterators
  требуют отдельного прохода. Нельзя на основании этого обзора заявлять
  отсутствие всех UB, UAF, утечек или исключительных путей.
