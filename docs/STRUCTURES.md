# Модели, значения и JSON

Модели проекта — обычные владеющие C++-объекты. Строка `std::string` хранит
свои байты; `std::vector<T>` хранит свои элементы. Это обычные значения, их
можно копировать и возвращать по значению. Они не являются shared-memory
записями и не требуют `release()`.

## Откуда берутся модели

- `src/api/models.def` описывает поля внешнего JSON.
- `src/api/models.hpp` с помощью макросов объявляет C++ structs.
- `src/api/json.hpp` из той же схемы строит сериализацию и разбор JSON.
- `src/common/types.hpp` содержит `SearchInput`, потому что он нужен API, Core
  и IPC.

Схема `YANI_FIELD_JSON(type, member, "wire_name")` позволяет назвать C++ поле
удобно, сохранив ключ внешнего JSON. Примеры: `class_` ↔ `class`, `new_` ↔
`new`, `public_` ↔ `public`.

## Где проходит граница процесса

Core хранит API structs в `unordered_map` и `optional`. Перед IPC nlohmann-json
сериализует значения в обычный UTF-8 JSON. На стороне клиента это независимая
копия. Клиент может держать её сколько угодно и не должен обращаться за
указателем или handle к серверу.

Большинство IPC моделей совпадает с соответствующим JSON API объектом. Есть
важное исключение: `Server::animeToJson` преобразует подробный Anime перед
отправкой. `AnimeResult.videos` становится `players → dubbers → episodes`, а
`videos` в IPC JSON удаляется. Поля этого формата описаны в
[IPC-спецификации](../src/server/IPC.md#anime-и-video-json).

## Правило изменения схемы

1. Измените `models.def` и проверьте подходящий default/конвертацию в
   `json.hpp`.
2. Обновите API-справочник `API_MODELS.md`.
3. Соберите `api`, затем приложение, чтобы обнаружить ошибки преобразования.
4. Если это поле видно клиенту, проверьте API JSON и отдельную IPC-сериализацию.
5. Если поменялась форма IPC, обновите `src/server/IPC.md`, `docs/SERVER.md`,
   README-пример при необходимости и все клиенты.

Не меняйте имена JSON-полей только из-за того, что C++-имя неудобно. Используйте
`YANI_FIELD_JSON`, чтобы отдельно задать wire name.
