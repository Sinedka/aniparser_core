# Архитектура

Проект состоит из слоёв API, Core и Server, а также отдельных IPC-клиентов.
Слои разделены, чтобы TUI или другой клиент не зависел от деталей HTTP и
хранения данных.

```text
┌────────────────────┐       JSON Lines        ┌──────────────────────┐
│ TUI / ваш клиент   │ ◀─────────────────────▶ │ IpcServer            │
└────────────────────┘                          │ src/server           │
                                                └──────────┬───────────┘
                                                           │ вызовы методов
                                                ┌──────────▼───────────┐
                                                │ Server               │
                                                │ фасад + сериализация │
                                                └──────────┬───────────┘
                                                           │
                                                ┌──────────▼───────────┐
                                                │ Core                 │
                                                │ кэш + очередь задач  │
                                                └──────────┬───────────┘
                                                           │ HTTP
                                                ┌──────────▼───────────┐
                                                │ API yani.tv / Kodik  │
                                                │ AniLibria            │
                                                └──────────────────────┘
```

## Каталоги

| Путь | Что в нём находится |
| --- | --- |
| `src/api/` | HTTP-клиент, JSON-модели сайта, Kodik/Aksor extractors и клиент AniLibria. |
| `src/api/types.hpp` | Типы запросов API, включая `SearchInput`; отдельной `common`-цели нет. |
| `src/core/` | Anime, Search/Feed, история/избранное/статусы и пул фоновых задач. |
| `src/core/cache/` | AnimeCache, общий `AnimeCollection`, модели состояния и SaveManager; CMake-цель `aniparser_cache`. |
| `src/server/` | Фасад `Server`, JSON IPC и запуск сервера. |
| `src/server/ipc/` | Unix socket и Windows named pipe; CMake выбирает реализацию платформы. |
| `src/app/` | Ручной исполняемый пример API. |
| `tests/` | Автономные регрессионные проверки. |
| `tui/` | Linux TUI-клиент. Подключается к серверу только через IPC. |
| `docs/` | Этот справочник. |
| `out/` | CMake build tree; его не следует коммитить. |

## Один запрос по шагам

Например, клиент отправил `subscribeAnime` с `anime_id: 771`.

1. Клиент записывает JSON и `\n` в открытый IPC stream.
2. `IpcServer` читает полную строку, разбирает JSON, проверяет `method` и
   обязательное поле.
3. `Server` передаёт запрос в `Core`.
4. Core под mutex получает текущий снимок и решает, истёк ли его пятиминутный
   TTL. Callback с текущим снимком вызывается сразу.
5. Если записи нет или она устарела, Core добавляет HTTP-задачу в очередь.
   Worker вызывает `yani::getAnime` из `src/api/api.cpp`.
6. После успешного ответа Core обновляет кэш и вызывает callback повторно,
   пометив значение как обновлённое.
7. IPC отправляет клиенту JSON-событие `anime.updated` с тем же `id`.

Коллекции истории, избранного и статусов обрабатываются локально Core и не
обращаются к API при добавлении или удалении ID. Подписка отдаёт страницу сразу;
если карточек аниме нет в Anime-кэше, Core отдельно загружает метаданные только
для ID текущей страницы через Search.

При ошибке обновления Anime, Feed или Search Core оставляет предыдущий снимок
в кэше. Клиент получает терминальное событие `*.updated` с `ok:false`,
`error` и `status`.

## Главная граница: JSON

IPC отправляет полные самодостаточные JSON-значения. Строки и векторы живут на
стороне клиента после получения. Между процессами не передаются адреса,
указатели, C++-объекты, shared memory, дескрипторы кэша или команды освобождения.

У API-модели Anime поле называется `videos` и хранит плоский список видео.
Перед отправкой клиенту `Server::animeToJson` заменяет его на:

```text
players[] → dubbers[] → episodes[]
```

В эту структуру попадают только записи с поддержанным iframe-плеером и
непустыми названиями плеера/озвучки. Эпизоды сортируются численно по номеру.
Это преобразование относится к IPC-сериализации; API-модель в `src/api/`
остаётся с полем `videos`.

AniLibria загружается отдельным IPC-методом `getAnilibriaVideos(anime_id)`:
TUI не смешивает его серии с `players` из Anime JSON. При построении списка
источников оно добавляет AniLibria, если в Anime есть
`remote_ids.anilibria_alias`; после выбора запрашивает прямые HLS-ссылки всех
серий и показывает доступные качества для копирования. Сам AniLibria-вызов
синхронно обращается к API и не использует Anime-кэш Core.

## Почему кэш находится в Core

Core централизует конкурентный доступ, TTL и объединение сведений из поиска и
feed. Server не хранит копию кэша и не передаёт клиенту ссылку на него. TUI
получает snapshot, а при обновлении заменяет или объединяет его локально.

Подробнее см. [Core](CORE.md), [кэш](CACHE.md) и [IPC](../INTEGRATION.md).

После исправлений аудита JSON dispatcher общий для обоих транспортов:
`src/server/ipc/protocol.hpp`; validation — `request_validation.hpp`. Платформенные
cpp содержат владение, I/O cancellation и lifecycle соединений.
`collection_changes.cpp` реализует подготовку и commit сохранений, а
`callback_queue.hpp` гарантирует initial snapshot перед completion callbacks.
TUI хранит owning navigation frames, включая модель и вложенные меню; возврат
не переносит старые индексы на данные другого аниме.
